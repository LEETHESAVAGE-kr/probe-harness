## 설명 준비 ($defend가 제출 전에 이 절만 채운다 · 빈 줄 빼고 60줄 이내 · 나는 읽기만)
### ① 구조 한 장
- server.js(라우트) → src/auth.js(로그인·역할) → src/enroll.js(신청·승격) → src/store.js(SQLite kv) → 응답 JSON
- 설정은 server.js 시작 때 PORT·DB_PATH·APP_TZ를 읽는다. 결과 검증기는 없음 — 그래서 정원 초과를 테스트로만 막는다.
### ② 기준과 이유
- 신청 순서대로 확정(먼저 온 사람 우선). 더 단순한 "추첨"은 담당자가 거부(10:44). 더 정교한 "우선순위 점수"는 근거가 없어 PLAN 한계의 대안으로만 적었다.
### ③ 숫자
- 입력 1,200명 = 사용 1,150 + 버림 50(휴면). 테스트 21/21. curl 6경로 200. 10배 입력 0.8초. 동시 신청 2개 → 200·409.
### ④ AI를 바로잡은 지점
- Codex가 정원 비교를 >로 써서 ≥로 고쳤다(카드 1). 대기 순번을 이름순으로 하자는 제안은 거부했다.
### ⑤ 한계·안 만든 것
- R5 운영자 화면의 그래프는 안 만듦 — 시간. 결제는 README 제외 범위.
### ⑥ 깨지는 조건
- 입력 10배: enroll()의 반별 인원 세기가 매번 전체를 훑는다 → 8초 이상 → 반별 인원을 저장한다.
- 동시 접속: 마지막 자리에 두 명 → 잠금 1개(lock.js)로 409. 서버를 둘 띄우면 깨진다.
- 외부 실패: DB 파일 잠김 → 500 → 재시도 없음. 기록 없음.
- 시간대: 마감 18시는 APP_TZ(Asia/Seoul) 기준 — 컨테이너 UTC여도 같다(feat_time 시험).
### 예상 문항
- Q1. 왜 신청 순서 방식인가? / 답: README는 정원만 정했다. 그래서 신청 순서로 확정했다. 담당자가 추첨을 거부했다(10:44). 같은 시각 동률은 ID 순이라 공정하지 않을 수 있다.
- Q2. 입력이 늘면 어디서 먼저 깨지나? / 답: enroll()이 매번 전체를 센다. 1배 0.08초, 10배 0.8초다. 100배면 8초로 예상한다. 반별 인원을 저장해 고친다.
- Q3. 동시에 접속하면? / 답: 쓰기는 lock.js 하나로 직렬화했다. 동시 신청 2개는 200·409였다. 읽기는 저장된 결과만 본다. 서버를 여러 개 띄우면 잠금이 안 통한다.
- Q4. 백엔드 구성은? / 답: server.js가 받는다. auth.js가 역할을 본다. enroll.js가 계산하고 store.js가 저장한다. 결과 검증기는 없다.
- Q5. 배포 전 고려사항은? / 답: Dockerfile·헬스체크·환경변수는 했다. 비밀번호 정책은 안 했다. 데모 계정 비밀번호가 기본값이다. 먼저 auth.js에서 기본값을 없앤다.
- Q6. 핵심 동작과 확인 방법은? / 답: 신청·승격이다. 테스트 21/21, curl 200을 봤다. 화면에서 30번째 신청이 확정되는 것을 봤다. 동률은 확인하지 않았다.
- Q7. AI 제안을 고친 부분은? / 답: 정원 비교를 ≥로 고쳤다. 담당자 기준이 30명이었다. 경계 테스트로 확인했다. 다른 비교는 다시 보지 않았다.
- Q8. 가장 약한 입력은? / 답: 같은 시각 신청 두 건이다. ID 순으로 정한다. 담당자에게 묻지 못했다. 기록 없음.
