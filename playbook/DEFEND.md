## 0. 뼈대 파일 7개 — 이름과 한 줄 (가장 먼저 외운다)

| 파일 | 함수 | 하는 일 한 줄 |
|---|---|---|
| `server.js` | `createApp`, `start`, `readBody`, `send` | 진입점. 요청을 읽고(`readBody`, 1MB 넘으면 413·JSON 깨지면 400), 경로별로 보내고, 응답(`send`). `start`가 0.0.0.0·PORT(기본 3000)로 띄운다 |
| `src/auth.js` | `seed`, `login`, `who`, `setCookie` | 빈 저장소면 데모 계정 둘(operator / member)을 만들고, 로그인하면 세션 쿠키를 준다. 쿠키는 **HttpOnly·Path만** |
| `src/lock.js` | `exclusive(name, work)` | 쓰기 작업을 한 번에 하나. 같은 이름이 진행 중이면 기다리지 않고 **409** |
| `src/store.js` | `openStore` → (돌려주는 객체의) `get`·`set` | 영속 저장. `node:sqlite`가 있으면 SQLite, 없으면 같은 경로의 JSON. 기본 경로 `./var/app.db` |
| `src/time.js` | `fmt`, `parseLocal`, `minuteOfDay` | 업무 시각을 **Asia/Seoul**로만 읽고 쓴다. 시스템 시간대가 UTC여도 UTC 22:30 → KST 07:30 |
| `src/validate_schema.js` | `schemaKeys`, `compare` | 내보내기 JSON의 키를 **스키마 md 표에서 읽어** 대조. 빠진 키·남는 키를 돌려준다 |
| `Dockerfile` | — | 의존성 0이라 `npm install` 없음. `/app/var` 만들고 `chown` 뒤 `USER node`. HEALTHCHECK는 `/health` |

**요청 한 번의 경로(구조 한 장) — 이 문장을 통째로 외운다:**

> "요청이 들어오면 `server.js`의 `createApp`이 받습니다. 먼저 `auth.who`로 쿠키에서 누구인지 보고, 역할이 안 맞으면 403, 로그인이 없으면 401을 돌려줍니다. 그다음 `readBody`로 본문을 읽고, `[입력 검증: 예 — 필수 칸을 검증한 뒤 / 없으면 빈칸]` 과제 계산은 `[계산 모듈 파일]`의 `[함수]`가 합니다. 쓰기 작업이면 `lock.exclusive`로 감싸서 실행이 겹치면 두 번째는 409입니다. 결과는 `store.set`으로 저장하고 `send`로 응답합니다. 내보내기는 `validate_schema.compare`로 키를 스키마 문서와 대조한 뒤 내보냅니다. 설정은 전부 환경변수에서 읽되 기본값이 있어 아무것도 안 줘도 뜹니다."

## 1. 카드 6장 — 네 마디(제 구현은 → 이유 → 확인은 → 한계는)

틀은 여섯 개로 고정한다. 변형은 '변형 문장' 한 줄로만 둔다. 값이 바뀌는 칸은 당일 숫자 다섯 개다: ① 테스트 n개 중 n개 통과 · ② 입력 n = 사용 n + 버림 n · ③ 지금 몇 초, 10배면 몇 초 · ④ 동시 결과 · ⑤ 담당자 기준값. 파일 이름은 server.js, lock.js, store.js, auth.js 넷만 부르고 나머지는 우리말로 부른다. 예시 답안의 '구내 주차장 배정'은 설명을 위한 가상 과제다.

### D1. 왜 그 방식으로 만들었나 (틀 A)
뼈대: 조건만 주어졌다 → 단순한 규칙으로 정했다 → 설명되고 담당자 기준으로 확인했다 → 더 단순한 건 조건을 깨고, 더 정교한 건 시간·설명 때문에 안 했다 → 약점과 대책

외울 답: 제 구현은 `[대상]`을 "`[규칙 한 문장: 예 — 조건을 만족하는 것 중 앞에서부터 고른다]`" 방식으로 `[배정/선택]`하는 계산 모듈입니다. 이유는 과제가 담당자 기준 `[⑤ 기준값]` 같은 조건만 주었고, 이 규칙은 그 조건을 그대로 코드로 옮긴 것이라 규칙대로 따라가면 누가 왜 뽑혔는지 따라가며 설명할 수 있기 때문입니다. 더 단순한 `[대안 1: 예 — 들어온 순서대로]`는 `[어기는 조건]`을 어기고, 더 정교한 `[대안 2: 예 — 가중치를 매겨 최적화]`는 `[안 고른 이유: 예 — 요구에 없고 결과를 설명하기 어려워]` 고르지 않았습니다. 확인은 테스트 `[① n개 중 n개]` 통과로 했고, 기준값과 딱 같은 경우를 `[포함/제외]`로 정한 것은 제 판단이고, 그것을 고정하는 경계 테스트를 따로 두었습니다. 입력 `[② n건 = 사용 n건 + 버림 n건]`도 결과 파일에서 맞춰 봤습니다. 한계는 `[약점: 예 — 자리가 모자랄 때 일부가 못 받는 것]`이고, 그땐 `[고칠 것 하나]`부터 고치겠습니다.

변형 문장: 충돌형이면 둘째 문장을 "두 조건이 부딪혀 담당자가 `[언제]` 답한 `[조건]`을 먼저 지켰고, 밀린 쪽은 `[얼마나]` 어긋납니다"로. AI 제안을 고친 것이 있으면 확인 문장 앞에 "AI가 `[무엇]`을 넣으려 했지만 요구서에 없어 제가 되돌렸습니다".

예시 문항(가상 과제): 주차 자리 배정을 왜 그 방식으로 설계했습니까? 더 단순하거나 정교한 대안은 무엇이었습니까?

예시 답안(가상 과제): 제 구현은 주차 자리를 "걸어오는 거리가 먼 사람부터, 기준 400m까지 우선 배정"하는 방식으로 나누는 계산 모듈입니다. 이유는 담당자가 준 조건이 거리 우선과 400m 기준 두 가지였고, 신청자를 거리 순으로 한 번 줄 세워 앞에서부터 자리를 주면 그 조건이 그대로 코드가 되어, 누가 왜 받았는지 한 줄로 설명할 수 있기 때문입니다. 더 단순한 '신청 순서대로'는 먼 사람이 늦게 내면 못 받아 거리 우선을 어기고, 더 정교한 '가중치를 매겨 최적화'는 담당자가 요구하지 않았고 결과를 설명하기 어려워 고르지 않았습니다. 확인은 테스트 21개 중 21개 통과로 했고, 정확히 400m인 사람을 우선 대상에 넣기로 한 것은 제 판단이고, 그것을 고정하는 경계 테스트를 따로 두었습니다. 신청 310건 중 294건을 썼고, 16건은 휴직·거리 미측정·중복·퇴직으로 버렸다는 것을 결과 파일에서 확인했습니다. 한계는 자리가 모자라면 우선 대상 안에서도 거리가 짧은 사람 일부가 못 받는 것이고, 그땐 못 받은 사람을 다음 배정에서 먼저 받도록 순번을 남기는 것부터 고치겠습니다.

### D2. 여러 사람이 동시에 접속하면 (틀 C)
뼈대: 쓰기와 읽기를 나눈다 → 쓰기는 한 번에 하나, 둘째는 거절 → 확인한 숫자 → 세션 위치 → 잠금의 한계와 먼저 넣을 것

외울 답: 제 구현은 `[질문의 동작: 예 — 재계산]`이 겹치면 lock.js로 하나만 받고, 나머지는 기다리게 하지 않고 바로 409로 거절합니다. 이유는 이 쓰기가 `[결과표]`를 통째로 다시 저장하는 일이라, `[겹침 위험: 계산에 기다리는 구간이 있으면 — 둘이 겹쳐 늦게 끝난 쪽이 앞 결과를 덮어쓰기 / 계산이 동기면 — 지금은 차례로 처리되지만 기다리는 구간이 생겨도 덮어쓰지 않게 막아 두기]` 때문입니다. 계산은 `[③ n초]`면 끝나서, 거절받은 사람이 잠시 뒤 다시 누르면 됩니다. 조회는 저장을 바꾸지 않으므로 잠그지 않습니다. 확인은 같은 요청 둘을 동시에 보내서 했고, `[④ 동시 결과]`가 나왔으며 끝난 뒤에는 다시 성공합니다. 로그인 세션은 `[저장 모듈/메모리]`에 있어 재시작하면 `[그대로 남습니다/다시 로그인해야 합니다]`. 한계는 이 잠금이 서버 한 대 안에서만 듣는다는 것이고, 서버를 둘로 늘리면 그땐 잠금과 저장을 DB 트랜잭션으로 옮기는 것부터 고치겠습니다.

변형 문장: 동시 결과가 둘 다 200이면 확인 문장을 "같은 요청 둘을 동시에 보냈더니 계산이 동기라 두 요청이 차례로 처리되어 둘 다 성공했고, 지연을 넣어 겹치게 하면 둘째가 409로 거절됩니다"로. 잠금이 없으면 "제 구현에는 쓰기 잠금이 없습니다. 그래서 동시에 쓰면 결과가 섞일 수 있고, 그땐 쓰기 잠금 하나부터 넣겠습니다". 읽기·사용자 증가 질문이면 조회 문장을 첫 문장으로 올리고 "느려지는 건 계산입니다"로 틀 B의 둘째 문장을 붙인다.

예시 문항(가상 과제): 운영자 두 명이 동시에 재계산을 누르면 어떻게 됩니까?

예시 답안(가상 과제): 제 구현은 운영자 두 명의 재계산이 겹치면 lock.js로 먼저 온 하나만 받고, 다른 하나는 기다리게 하지 않고 바로 409로 거절합니다. 이유는 재계산이 신청자 294건의 주차 배정표를 통째로 다시 저장하는 일이라, 지금은 차례로 처리되지만 기다리는 구간이 생겨도 늦게 끝난 쪽이 덮어쓰지 않게 막아 두기 때문입니다. 계산은 0.04초면 끝나서, 거절받은 운영자가 잠시 뒤 다시 누르면 됩니다. 조회는 저장을 바꾸지 않으므로 잠그지 않습니다. 확인은 재계산 요청 둘을 동시에 보냈더니 계산이 동기라 두 요청이 차례로 처리되어 둘 다 성공했고, 지연을 넣어 겹치게 하면 둘째가 409로 거절됩니다. 끝난 뒤에는 다시 성공했습니다. 로그인 세션은 저장 모듈에 있어 재시작해도 그대로 남습니다. 한계는 이 잠금이 서버 한 대 안에서만 듣는다는 것이고, 서버를 둘로 늘리면 그땐 잠금과 저장을 DB 트랜잭션으로 옮기는 것부터 고치겠습니다.

### D3. 입력이 늘면 어디서 먼저 깨지나 (틀 B)
뼈대: 깨지는 곳 하나(어느 모듈의 어떤 반복) → 지금 숫자와 10배 숫자 → 어떻게 드러나나 → 먼저 고칠 것 하나

외울 답: 제 구현은 입력이 열 배가 되면 먼저 깨질 곳이 `[모듈과 부분: 예 — 계산 모듈의 이중 반복 / store.js가 저장마다 결과 전체를 다시 쓰는 부분]`입니다. 이유는 계산 모듈은 지금 `[③ n건에 n초]`, 열 배에서 `[n초]`로 `[건수에 비례해/곱으로]` 늘었고, `[저장 방식: 예 — 저장은 한 건만 바뀌어도 결과 전체를 값 하나로 다시 쓰기]` 때문입니다. `[비례면: 그래서 계산은 버티고 저장이 먼저입니다 / 곱이면: 그래서 계산의 반복이 먼저입니다.]` 드러나는 모습은 `[예 — 요청이 시간 안에 못 끝나 버튼이 실패하는 것 / 저장이 길어져 그동안 다른 요청의 응답까지 늦어지는 것]`입니다. 확인은 열 배로 늘린 입력으로 계산 시간을 재고, `[저장 방식]`은 store.js 코드에서 본 것으로 했고, 저장이 먼저라는 것은 잰 값이 아니라 코드로 판단한 것입니다. 입력 `[② n = 사용 n + 버림 n]`이 맞는 것과 테스트 `[① n개 중 n개]` 통과도 확인했습니다. 한계는 `[열 배까지만, 그것도 계산만 쟀다는 것]`이고, 그땐 `[안 잰 부분: 예 — 저장 시간]`을 먼저 재고, `[고칠 것 하나: 예 — 후보를 미리 정렬해 순서대로 넘기기]`부터 고치겠습니다.

변형 문장: 데이터가 이상하면 → "제 구현은 `[빈칸·범위 밖·중복]` 행을 사유별로 버리고 그 수를 기록합니다. 완전히 같은 행이 두 번 든 중복은 검산 등식이 못 잡아 따로 셌습니다"로 시작하고 ② 검산으로 잇는다. 파일·저장소가 죽으면 → "제 구현은 파일이 없으면 빈 저장소를 새로 만들고, 저장이 실패하면 오류를 돌려주고 이전 결과를 그대로 둡니다"로 시작하고 뒤는 같다(저장 방식이 JSON 파일이면 파일은 그대로지만 재시작 전까지 메모리에는 새 값이 남는다).

예시 문항(가상 과제): 구성원이 열 배로 늘면 어디서 먼저 깨집니까?

예시 답안(가상 과제): 제 구현은 구성원이 열 배가 되면 먼저 깨질 곳이 계산 모듈이 아니라 store.js가 저장할 때마다 배정표 전체를 값 하나로 다시 쓰는 부분입니다. 이유는 계산 모듈은 신청자 294건에 0.04초, 열 배에서 0.4초로 건수에 비례해 늘어 버티지만, 저장은 한 건만 바뀌어도 배정표 전체를 다시 써서 표가 커지는 만큼 길어지기 때문입니다. 저장은 끝날 때까지 서버가 다른 일을 못 하는 방식이라, 그 시간이 길어지면 그동안 다른 요청의 응답까지 늦어지는 식으로 드러날 것입니다. 확인은 열 배로 늘린 입력으로 계산이 0.4초에 끝나는 것을 재고, store.js가 저장마다 배정표 전체를 쓰는 것을 코드에서 본 것으로 했습니다. 저장이 먼저라는 것은 잰 값이 아니라 이 코드로 판단한 것입니다. 입력 310건 = 사용 294건 + 버림 16건이 맞는 것과 테스트 21개 중 21개 통과도 확인했습니다. 한계는 계산만 열 배까지 쟀고 저장 시간은 따로 재지 않았다는 것이고, 그땐 열 배 입력의 저장 시간을 먼저 재고, store.js가 바뀐 건만 따로 저장하도록 그 부분부터 고치겠습니다.

### D4. 프로덕션 배포 전 고려사항 (틀 E)
뼈대: 배포 요구를 했다/안 했다로 먼저 가른다 → 안 한 것의 순서 셋 → 지금 코드에서 먼저 바꿀 파일 하나 → 확인 못 한 것은 못 했다고

외울 답: 제 구현은 배포 대비 중 세 가지는 했고, `[안 한 것: 예 — 여러 서버가 함께 쓰는 DB·쿠키 보안 옵션·요청 횟수 제한]`은 안 했습니다. 한 것은 첫째 서버 환경 시계가 UTC여도 시각은 코드에서 Asia/Seoul로 고정했고, 둘째 설정 파일이 없어도 기본값으로 서버가 뜨게 했고, 셋째 `[상태 확인 경로와 도커 설정 파일/상태 확인 경로]`를 두었습니다. 이유는 `[날짜가 걸린 판단: 예 — 마감일·재직 여부]`이 환경 시계에 따라 바뀌면 안 되고, 처음 받는 사람이 설정 없이 바로 띄워 봐야 하기 때문입니다. 확인은 테스트 `[① n개 중 n개]` 통과로 했고, 그중 시각 테스트에서 UTC 밤 10시 30분이 한국 시각 아침 7시 30분으로 나왔으며, 환경변수 없이 띄워 상태 확인 경로가 정상인 것도 봤습니다. 도커 빌드는 `[해서 상태 확인 경로가 정상인 것을 봤습니다/환경에 도커가 없어 못 했고 기록에 건너뜀으로 남겼습니다/도커 설정을 두지 않아 하지 않았습니다]`. 내놓기 전 순서는 첫째 저장을 여러 서버가 함께 쓰는 DB로 옮기고, 둘째 로그인 쿠키에 보안 옵션을 켜고, 셋째 요청 횟수에 제한을 거는 것입니다. 한계는 저장이 `[한 대 서버의 파일]`이라 서버를 늘리면 잠금과 저장 내용이 서버마다 따로 놀 수 있다는 것이고, 그땐 store.js부터 여러 서버가 함께 쓰는 DB로 바꿔 고치겠습니다.

변형 문장: 보안을 물으면 '내놓기 전 순서' 둘째·셋째를 앞으로 올린다. 장애를 물으면 "저장이 실패하면 오류를 돌려주고 이전 결과는 유지하며, 파일이 없으면 빈 저장소로 시작합니다"를 넣는다(틀 B 변형과 같음). 못 본 걸 봤다고 하지 않는다.

예시 문항(가상 과제): 프로덕션에 배포하기 전에 무엇을 고려해야 합니까?

예시 답안(가상 과제): 제 구현은 배포 대비 중 세 가지는 했고, 여러 서버가 함께 쓰는 DB·쿠키 보안 옵션·요청 횟수 제한은 안 했습니다. 한 것은 첫째 서버 환경 시계가 UTC여도 시각은 코드에서 Asia/Seoul로 고정했고, 둘째 설정 파일이 없어도 기본값으로 서버가 뜨게 했고, 셋째 상태 확인 경로와 도커 설정 파일을 두었습니다. 이유는 휴직·퇴직자를 가르는 날짜 판단이 환경 시계에 따라 하루 밀리면 안 되고, 처음 받는 사람이 설정 없이 바로 띄워 봐야 하기 때문입니다. 확인은 테스트 21개 중 21개 통과로 했고, 그중 시각 테스트에서 UTC 밤 10시 30분이 한국 시각 아침 7시 30분으로 나왔으며, 환경변수 없이 띄워 상태 확인 경로가 정상인 것도 봤습니다. 도커 빌드는 실행 환경에 도커가 없어 못 했고 기록에 건너뜀으로 남겼습니다. 내놓기 전 순서는 첫째 저장을 여러 서버가 함께 쓰는 DB로 옮기고, 둘째 로그인 쿠키에 보안 옵션을 켜고, 셋째 요청 횟수에 제한을 거는 것입니다. 한계는 저장이 한 대 서버의 파일이라 서버를 늘리면 잠금과 배정 기록이 서버마다 따로 놀 수 있다는 것이고, 그땐 store.js부터 여러 서버가 함께 쓰는 DB로 바꿔 고치겠습니다.

### D6. 백엔드 구성과 코드 연결 (틀 D, 0장 구조 한 장과 같은 순서)
뼈대: 입구부터 응답까지 모듈 순서 한 줄 → 각 모듈 한 줄 → 설정·저장을 읽는 곳 → 없는 단계는 "없다, 그래서"

외울 답: 제 구현은 server.js 입구 하나에 로그인, 본문 읽기, 잠금, 계산, 저장 모듈을 차례로 잇는 구성입니다. 요청이 오면 auth.js가 쿠키로 사용자를 확인하고, server.js가 본문을 읽어 1MB가 넘으면 413, 깨진 JSON이면 400으로 돌려보냅니다. `[입력 검증: 예 — 필수 칸을 검증한 뒤 / 없으면 빈칸]` lock.js로 쓰기를 잠근 채 계산 모듈이 담당자 기준 `[⑤ 기준값]`으로 결과를 만들고 store.js가 `[SQLite/JSON 파일]`에 저장하고 응답합니다. 설정은 전부 환경변수에서 읽되 기본값이 있어 아무것도 안 줘도 뜨고, 저장소가 비어 있으면 시작할 때 데모 계정 둘을 만듭니다. 이렇게 나눈 이유는 모듈마다 책임을 하나로 두어 `[⑤ 기준값]` 경계 같은 계산만 따로 테스트할 수 있고, 과제가 바뀌어도 미리 검증한 공통 모듈은 두고 계산 모듈만 바꾸면 되기 때문입니다. 그래서 AI에게도 `[맡긴 범위: 예 — 계산 모듈과 그 테스트]`만 맡겨 고칠 범위를 좁혔습니다. 확인은 테스트 `[① n개 중 n개]` 통과와, 서버를 띄워 정상 요청엔 200, 깨진 JSON엔 400을 받은 것, 같은 쓰기 둘을 동시에 보내 `[④ 동시 결과]`가 나온 것으로 했습니다. 한계는 결과를 기준과 다시 대조하는 단계가 없어 계산이 틀리면 그대로 저장된다는 것이고, 그땐 결과를 `[⑤ 기준값]`과 대조하는 검증 스크립트부터 넣어 고치겠습니다.

변형 문장: 인증을 물으면 첫 문장을 "제 구현은 auth.js가 쿠키로 사용자를 확인하는 인증 방식입니다"로 바꾸고 `[비밀번호 해시 저장·스크립트가 못 읽는 쿠키·경로별 권한 확인 중 실제로 한 것]`을 잇는다. 왜 나눴는지를 물으면 첫 문장을 "제 구현은 모듈마다 책임을 하나로 나눈 구조입니다"로 하고 '나눈 이유' 문장부터 쓴다.

예시 문항(가상 과제): 백엔드 구성과 코드가 어떻게 연결되는지 설명하십시오.

예시 답안(가상 과제): 제 구현은 server.js 입구 하나에 로그인, 본문 읽기, 잠금, 계산, 저장 모듈을 차례로 잇는 구성입니다. 요청이 오면 auth.js가 쿠키로 사용자를 확인하고, server.js가 본문을 읽어 1MB가 넘으면 413, 깨진 JSON이면 400으로 돌려보냅니다. 거리·사번을 검증한 뒤 lock.js로 쓰기를 잠근 채 계산 모듈이 담당자 기준 400m로 먼 사람부터 배정하고 store.js가 SQLite에 배정표를 저장하고 응답합니다. 설정은 전부 환경변수에서 읽되 기본값이 있어 아무것도 안 줘도 뜨고, 저장소가 비어 있으면 운영자·일반 데모 계정 둘을 만듭니다. 이렇게 나눈 이유는 모듈마다 책임을 하나로 두어 400m 경계 같은 계산만 따로 테스트할 수 있고, 과제가 바뀌어도 미리 검증한 공통 모듈은 두고 계산 모듈만 바꾸면 되기 때문입니다. 그래서 AI에게도 계산 모듈과 그 테스트만 맡겨 고칠 범위를 좁혔습니다. 확인은 테스트 21개 중 21개 통과와, 서버를 띄워 정상 요청엔 200, 깨진 JSON엔 400을 받은 것, 배정 요청 둘을 동시에 보내 계산이 동기라 차례로 처리되어 둘 다 성공한 것으로 했고, 지연을 넣어 겹치게 하면 둘째가 409로 거절됩니다. 한계는 입력은 검증하지만 배정 결과를 기준과 다시 대조하는 단계가 없어 계산이 틀리면 그대로 저장된다는 것이고, 그땐 배정표를 기준 400m와 대조하는 검증 스크립트부터 넣어 고치겠습니다.

### F. 핵심 동작과 확인한 방법 (틀 F, D1 근거 + D3 + 퀴즈)
뼈대: 기능 하나를 모듈로 → 세 겹으로 확인(테스트·직접 호출·화면) → 숫자 → AI와 나의 분담 한 문장 → 못 본 것

외울 답: 제 구현은 `[기능 하나]`가 핵심 동작이고, 계산 모듈 한 곳에 모아 세 겹으로 확인했습니다. 이유는 담당자가 준 기준 `[⑤ 기준값]`이 결과를 가르는 지점이라, 그 계산을 서버·저장과 떼어 따로 테스트하려 했기 때문입니다. 확인은 세 겹으로 했습니다. 첫째, 테스트 `[① n개 중 n개]` 통과이고 그중 하나는 기준값과 딱 같은 경계값입니다. 둘째, 서버를 띄워 `[경로]`를 직접 호출해 `[응답]`을 받았고 기록으로 남겼습니다. 셋째, 화면에서 `[본 값 하나]`를 눈으로 봤습니다. 데이터는 입력 `[② n = 사용 n + 버림 n]`으로 검산했습니다. AI에게는 `[맡긴 일]`을 목적·범위·내 판단·확인 네 줄 지시로 맡겼고, 숫자는 제가 결과 파일을 열어 맞췄습니다. 한계는 `[못 본 것: 예 — 브라우저 여러 개 동시 접속]`이고, 그땐 `[그 확인]`부터 넣어 고치겠습니다.

변형 문장: AI 협업·고친 부분을 물으면 AI 문장 자리에 "AI가 `[무엇]`을 넣으려 했는데 요구서에 없어 되돌렸고, 그 뒤로 지시마다 범위를 붙였습니다"를 넣는다. 코드를 이해했는지 물으면(기록에 퀴즈가 있을 때만) AI 문장 뒤에 "기능마다 맞는 설명과 미묘하게 틀린 설명을 섞어 내게 해, 코드를 안 보고 고르는 방식으로 확인했습니다"를 붙인다. 확인 못 한 것을 물으면 "그건 확인하지 않았습니다. 확인하려면 `[어느 기록]`을 보면 됩니다"로 한계 문장을 대신한다.

예시 문항(가상 과제): 핵심 동작은 무엇이고 어떻게 확인했습니까?

예시 답안(가상 과제): 제 구현은 걸어오는 거리가 먼 신청자부터 자리를 주는 거리 우선 배정이 핵심 동작이고, 계산 모듈 한 곳에 모아 세 겹으로 확인했습니다. 이유는 담당자가 준 기준 400m가 우선 배정을 가르는 지점이라, 그 계산을 서버·저장과 떼어 따로 테스트하려 했기 때문입니다. 확인은 세 겹으로 했습니다. 첫째, 테스트 21개 중 21개 통과이고 그중 하나는 딱 400m인 신청자가 우선에 들어가는 경계값입니다. 둘째, 서버를 띄워 배정 경로를 직접 호출해 200을 받았고 기록으로 남겼습니다. 셋째, 화면에서 가장 먼 신청자가 첫 자리를 받은 것을 봤습니다. 데이터는 입력 310건 = 사용 294건 + 버림 16건(휴직·거리 미측정·중복·퇴직)으로 검산했습니다. AI에게는 계산 모듈과 테스트 초안을 네 줄 지시로 맡기고 경계값은 제가 정했으며, 숫자는 제가 결과 파일을 열어 맞췄습니다. 한계는 브라우저 여러 개로 동시에 접속한 화면은 직접 보지 못했다는 것이고(동시 요청은 요청을 직접 보내 봤습니다), 그땐 그 화면 확인부터 넣어 고치겠습니다.

### 참고 카드 D5. 스키마 문서에서 키를 읽어 대조 (틀 밖 — 내보내기를 물을 때만)
제 구현은 키 이름을 코드에 박지 않고 스키마 문서에서 읽어 대조합니다. 이유는 키 이름이 한 글자만 달라도 형식 검증을 통과하지 못하기 때문입니다. 확인은 한 글자 다른 키가 빠진 키와 남는 키 둘 다로 잡힌 테스트와, 실제 내보내기 샘플 `[out/파일]`의 `[ok / missing n·extra n]`으로 했습니다. 한계는 키 이름만 보고 값의 타입이나 범위는 안 본다는 것이고, 그땐 키 대조 바로 뒤에 값 검사를 넣어 고치겠습니다.

## 4. 쓰지 않는 말 → 대신 쓰는 말

| 쓰지 않는다 | 대신 |
|---|---|
| "테스트했습니다" | "테스트 `[n]`개 중 `[n]`개 통과, `out/test_result.txt`에 있습니다" |
| "더 확인이 필요합니다" | "확인하려면 `[파일·명령]`을 보면 됩니다. 저는 `[무엇]`까지 봤습니다" |
| "AI가 그렇게 만들어서" | "제가 `[무엇]`을 그렇게 두기로 했습니다. 이유는 `[…]`" |
| "제가 직접 썼습니다"(DECISIONS·AI_COLLABORATION·4문장) | "Codex가 후보를 내고 제가 `[번호]`로 골랐습니다. 고른 이유는 `[…]`, 근거는 `[out 파일]`입니다" |
| "시간이 없어서" | "`[R번호]`는 안 만들 것으로 두었고 사유는 `[…]`입니다. 만든 것은 끝까지 확인했습니다" |
| "잘 돌아갑니다" | "`[경로]`가 200이고 화면에서 `[값]`을 봤습니다" |
| 모르는 걸 아는 척 | "그건 확인하지 않았습니다. 확인하려면 `[A]`를 보면 됩니다" |
| 안 한 측정을 한 척 | "그건 재지 않았습니다. 재려면 `[무엇]`을 돌리면 됩니다" |

## 네 마디 골격 (40초)
```
시작  "제 구현은 X입니다."                  ← 모듈 이름
이유  "이유는 Y이기 때문입니다."             ← 담당자 기준
확인  "확인은 Z로 했습니다."                 ← 숫자 2~3개
한계  "한계는 W이고, 그땐 V부터 고치겠습니다."  ← 신뢰
```
- 질문의 전제가 내 구현과 다르면 차이를 먼저 밝힌다: "질문의 전제 …는 제 구현과 다릅니다, 실제로는 …".
- 3분쯤 핵심을 먼저 적고 나머지를 보강한다. "더 확인해야 합니다"로 끝내지 않는다 — "확인하려면 A(파일·명령)를 보면 됩니다".

## 세 가지 금지
| 금지 | 대신 |
|---|---|
| 모르는 걸 아는 척 | "그건 확인하지 않았습니다. 확인하려면 A를 보면 됩니다." |
| 근거 없는 "테스트했습니다" | "테스트 n개 중 n개 통과, out/test_result.txt에 있습니다." |
| AI 탓·시간 탓 | "제가 X를 안 만들 것으로 뒀습니다. 이유는 Y입니다." |

## 제출 확정 뒤 대기 5~10분
1. "설명 준비" ①③⑥을 한 번 더 읽는다.
2. 위 6유형을 하나씩 소리 내어 네 마디로 답한다. 막히면 그건 기록에 없는 것이다 → 서술형에서 정직하게 연다.
