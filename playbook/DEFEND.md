## 1. 카드 6장 — 네 마디(제 구현은 → 이유 → 확인은 → 한계는)

틀은 여섯 개로 고정한다. 변형은 '변형 문장' 한두 줄로만 둔다. 여섯 틀이 같은 네 마디로 짜여 있어, 아래 공통 문장은 한 번만 외운다: "확인은 테스트 `[①]`개가 모두 통과한 것과 ~로 했습니다" · "한계는 ~이고, 그땐 ~부터 고치겠습니다". 당일 값은 넷이다: ① 테스트 몇 개가 모두 통과 · ② 들어온·쓴·버린 건수 · ③ 열 배 입력의 계산 시간 · ④ 담당자 기준값. 파일 이름은 server.js, auth.js, lock.js, store.js 넷만 부르고 나머지는 우리말로 부른다. 예시 답안의 '구내 주차장 배정'은 설명을 위한 가상 과제다.

### D1. 왜 그 방식으로 만들었나 (틀 A)
뼈대: 담당자 조건 → 그 조건을 그대로 옮긴 규칙 → 더 단순한 건 조건을 깨고, 더 정교한 건 요구에 없고 설명이 어렵다 → 테스트로 순서와 경계를 고정 → 약점과 먼저 고칠 것

외울 답: 제 구현은 `[대상]`을 `[규칙 한 줄]` 방식으로 고르는 계산 모듈입니다. 이유는 담당자가 준 조건이 `[조건과 ④ 기준값]`이었고, 이 규칙은 그 조건을 그대로 코드로 옮긴 것이라 누가 왜 뽑혔는지 바로 설명할 수 있기 때문입니다. 더 단순한 `[들어온 순서대로]`는 그 조건을 어기고, 더 정교한 최적화는 요구에 없고 결과를 설명하기 어려워 고르지 않았습니다. 확인은 테스트 `[①]`개가 모두 통과한 것으로 했고, 그중 `[규칙대로 순서가 나오는지]`와 기준값과 딱 같은 경우가 `[드는지/빠지는지]`를 따로 고정했습니다. 한계는 `[약점]`이고, 그땐 `[고칠 것]`부터 고치겠습니다.

변형 문장: 규칙 둘이 부딪히면 이유 문장을 "두 조건이 부딪혀 담당자가 답한 `[조건]`을 먼저 지켰습니다"로.

예시 문항(가상 과제): 주차 자리 배정을 왜 그 방식으로 설계했습니까? 더 단순하거나 정교한 대안은 무엇이었습니까?

예시 답안(가상 과제): 제 구현은 주차 자리를 걸어오는 거리가 먼 사람부터 주고, 400m 이상이면 우선 대상으로 두는 계산 모듈입니다. 이유는 담당자가 준 조건이 거리 우선과 400m 기준 두 가지였고, 이 규칙은 그 조건을 그대로 코드로 옮긴 것이라 누가 왜 받았는지 바로 설명할 수 있기 때문입니다. 더 단순한 신청 순서대로는 먼 사람이 늦게 내면 못 받아 거리 우선을 어기고, 더 정교한 최적화는 요구에 없고 결과를 설명하기 어려워 고르지 않았습니다. 확인은 테스트 21개가 모두 통과한 것으로 했고, 그중 먼 순서대로 나오는지와 딱 400m인 사람이 우선에 드는지를 따로 고정했습니다. 한계는 자리가 모자라면 우선 대상 중에도 못 받는 사람이 생기는 것이고, 그땐 못 받은 사람이 다음 배정에서 먼저 받도록 순번을 남기는 것부터 고치겠습니다.

### D3·D2. 입력이 늘거나 동시에 몰리면 (틀 B)
뼈대: 계산은 버티고 저장이 먼저(추정) + 겹치는 쓰기는 하나만 받고 409 → 열 배 계산 시간·저장 방식·덮어쓰기 위험 → 열 배 측정과 동시 요청 둘 → 잰 것과 코드로 판단한 것을 가른다 → 저장 시간 미측정·서버 한 대 잠금의 한계

외울 답: 제 구현은 입력이 열 배가 되면 계산은 버티고 저장이 먼저 느려질 것으로 보고, 같은 쓰기가 동시에 오면 lock.js로 하나만 받고 나머지는 바로 409로 거절합니다. 이유는 계산은 열 배에서 `[③ 몇 초]`로 건수만큼만 늘었지만, store.js는 한 건만 바뀌어도 결과 전체를 다시 쓰고, 쓰기가 겹치면 늦게 끝난 쪽이 앞 결과를 덮어쓸 수 있기 때문입니다. 조회는 결과를 바꾸지 않으므로 잠그지 않습니다. 확인은 열 배 입력으로 계산 시간을 재고, 같은 요청 둘을 동시에 보낸 것으로 했습니다. 계산이 짧아 둘 다 차례로 성공했고, 계산에 잠깐 기다림을 넣어 겹치게 하면 둘째가 409로 거절되고, 거절된 사람은 잠시 뒤 다시 누르면 됩니다. 저장이 먼저라는 것은 잰 값이 아니라 코드를 보고 판단한 것입니다. 한계는 저장 시간은 따로 재지 않았고 잠금이 서버 한 대 안에서만 듣는다는 것이고, 그땐 바뀐 건만 저장하도록 store.js부터 고치겠습니다.

변형 문장: 계산이 몇 배 이상으로 늘었으면 첫 문장을 "계산 모듈의 겹친 반복이 먼저 느려지고"로. 동시에 보냈을 때 바로 하나가 거절됐으면 "하나는 성공, 하나는 409로 거절됐습니다"로. 이상한 데이터를 물으면 첫 문장을 "제 구현은 빈칸·범위 밖·중복 행을 사유별로 버리고 그 수를 기록합니다"로.

예시 문항(가상 과제): 구성원이 열 배로 늘고, 운영자 여럿이 동시에 재계산을 누르면 어떻게 됩니까?

예시 답안(가상 과제): 제 구현은 구성원이 열 배가 되면 계산은 버티고 저장이 먼저 느려질 것으로 보고, 재계산이 동시에 오면 lock.js로 하나만 받고 나머지는 바로 409로 거절합니다. 이유는 계산은 열 배에서 0.4초로 건수만큼만 늘었지만, store.js는 한 건만 바뀌어도 배정표 전체를 다시 쓰고, 재계산이 겹치면 늦게 끝난 쪽이 앞 배정표를 덮어쓸 수 있기 때문입니다. 조회는 배정표를 바꾸지 않으므로 잠그지 않습니다. 확인은 열 배 입력으로 계산 시간을 재고, 같은 요청 둘을 동시에 보낸 것으로 했습니다. 계산이 짧아 둘 다 차례로 성공했고, 계산에 잠깐 기다림을 넣어 겹치게 하면 둘째가 409로 거절되고, 거절된 사람은 잠시 뒤 다시 누르면 됩니다. 저장이 먼저라는 것은 잰 값이 아니라 코드를 보고 판단한 것입니다. 한계는 저장 시간은 따로 재지 않았고 잠금이 서버 한 대 안에서만 듣는다는 것이고, 그땐 바뀐 건만 저장하도록 store.js부터 고치겠습니다.

### C. AI에게 시킨 것과 내가 바꾼 것 (틀 C)
뼈대: 맡긴 일과 내가 정한 것 → 되돌린 사례 하나 → 되돌린 이유 → 그 뒤 지시 방식과 내가 고른 것 → 되돌린 것과 숫자를 내가 확인 → 직접 계산 못 한 기대값

외울 답: 제 구현은 AI에게 `[맡긴 일]`을 맡기고, 기준과 범위는 제가 정했습니다. 대표 사례로 AI가 요구에 없는 `[AI 제안]`을 넣으려 해서 제가 되돌렸습니다. 이유는 요구에 없는 기능은 담당자가 확인할 기준이 없고, 핵심 기능을 확인할 시간만 줄이기 때문입니다. 그 뒤로는 지시마다 목적, 범위, 내 판단, 확인 네 줄을 붙였고, `[내가 고른 것]`도 AI가 낸 후보 중 제가 골라 이유를 작업 기록에 남겼습니다. 확인은 되돌린 뒤 바뀐 내용을 비교해 그 코드가 남지 않은 것을 보고, 테스트 `[①]`개가 모두 통과한 것으로 했고, 숫자는 제가 결과 파일을 열어 맞췄습니다. 한계는 AI가 쓴 테스트 중 경계값 말고 나머지 기대값을 제가 직접 계산해 보지 못한 것이고, 그땐 그 기대값부터 손으로 계산해 고치겠습니다.

변형 문장: 도구·설정을 물으면 첫 문장을 "제 구현은 Codex를 승인 모드로 돌려 명령마다 제가 보고 허락했고, 탭을 구현·문서·측정으로 나눠 만들었습니다"로. 되돌린 사례가 없으면 둘째 문장을 "AI가 낸 `[무엇]`을 제가 `[어떻게]` 바꿨습니다"로 — 없는 사례는 만들지 않는다.

예시 문항(가상 과제): AI와 어떻게 일했고, AI의 제안을 직접 바꾼 부분은 무엇입니까?

예시 답안(가상 과제): 제 구현은 AI에게 계산 모듈과 테스트 초안을 맡기고, 기준과 범위는 제가 정했습니다. 대표 사례로 AI가 요구에 없는 배정 결과 문자 알림을 넣으려 해서 제가 되돌렸습니다. 이유는 요구에 없는 기능은 담당자가 확인할 기준이 없고, 거리 우선 배정을 확인할 시간만 줄이기 때문입니다. 그 뒤로는 지시마다 목적, 범위, 내 판단, 확인 네 줄을 붙였고, 딱 400m를 넣을지도 AI가 낸 두 후보 중 제가 골라 이유를 작업 기록에 남겼습니다. 확인은 되돌린 뒤 바뀐 내용을 비교해 알림 코드가 남지 않은 것을 보고, 테스트 21개가 모두 통과한 것으로 했고, 숫자는 제가 결과 파일을 열어 맞췄습니다. 한계는 AI가 쓴 테스트 중 경계값 말고 나머지 기대값을 제가 직접 계산해 보지 못한 것이고, 그땐 그 기대값부터 손으로 계산해 고치겠습니다.

### D6. 구조와 코드 연결 · 권한 (틀 D, 0장 구조 한 장과 같은 순서)
뼈대: 입구부터 저장까지 순서 한 줄 → 각 모듈 한 줄 → 담당자 기준이 계산 모듈 한 곳에 있다 → 테스트와 서버를 띄워 본 결과 → 결과를 기준과 다시 맞춰 보는 단계가 없다

외울 답: 제 구현은 server.js 하나가 요청을 받아 로그인 확인, 입력 검증, 잠금, 계산, 저장 순서로 넘기는 구조입니다. auth.js가 쿠키로 사용자를 확인하고, 입력이 깨졌으면 400으로 돌려보내고, lock.js가 쓰기를 잠근 뒤, 계산 모듈이 담당자 기준 `[④]`으로 결과를 만들고 store.js가 저장합니다. 설정은 기본값이 있어 아무것도 안 줘도 뜨고, 저장소가 비어 있으면 데모 계정 둘을 만듭니다. 이렇게 나눈 이유는 담당자 기준이 계산 모듈 한 곳에만 있어 그것만 떼어 테스트할 수 있고, 기준이 바뀌어도 그 모듈만 고치면 되기 때문입니다. 확인은 테스트 `[①]`개가 모두 통과한 것과, 서버를 띄워 정상 요청은 성공하고 깨진 입력은 거절되는 것을 본 것으로 했습니다. 한계는 결과를 기준과 다시 맞춰 보는 단계가 없어 계산이 틀리면 그대로 저장된다는 것이고, 그땐 결과를 기준값과 대조하는 검증부터 넣어 고치겠습니다.

외울 답(권한만 물을 때 — 구조 답의 둘째 문장을 펼친 것): 제 구현은 로그인한 사람의 역할로 권한을 나눕니다. auth.js가 본문을 읽기 전에 쿠키를 보고, 로그인이 없으면 401, 역할이 안 맞으면 403을 돌려줍니다. `[바꾸는 일]`은 운영자만, `[조회]`는 둘 다 할 수 있습니다. 이유는 화면에서 버튼을 숨기는 것만으로는 주소를 직접 부르는 요청을 못 막고, 계산보다 먼저 막아야 결과를 건드리지 못하기 때문입니다. 확인은 로그인 없이 부르면 401, 일반 계정은 403, 운영자는 성공하는 것을 테스트로 고정한 것으로 했습니다. 한계는 데모 비밀번호가 코드의 기본값이라는 것이고, 그땐 비밀번호를 환경변수로 받는 것부터 고치겠습니다.

### D4. 배포 전에 고려할 것 (틀 E)
뼈대: 한 것 셋과 남은 것을 첫 문장에서 가른다 → 날짜 판단·처음 받는 사람 → 시각 테스트와 설정 없이 띄운 상태 확인 → 도커는 한 대로만 → 서버 한 대 파일 저장의 한계와 먼저 옮길 것

외울 답: 제 구현은 배포 대비로 세 가지는 했고, 여러 서버가 함께 쓰는 DB와 쿠키 보안, 요청 횟수 제한, 데모 계정 끄기는 아직 남았습니다. 한 것은 시각을 한국 시간으로 고정했고, 설정 없이도 기본값으로 뜨게 했고, 상태 확인 경로를 두었습니다. 이유는 `[날짜가 걸린 판단]`이 서버 시계에 따라 하루 밀리면 안 되고, 처음 받는 사람이 바로 띄워 봐야 하기 때문입니다. 확인은 서버 시계와 상관없이 한국 시각이 나오는 시각 테스트를 포함해 테스트 `[①]`개가 모두 통과한 것과, 설정 없이 띄워 상태 확인이 정상인 것을 본 것으로 했습니다. 도커는 `[돌려 봤습니다 / 환경에 없어 돌리지 못했고 기록에 건너뜀으로 남겼습니다]`. 한계는 저장이 서버 한 대의 파일이라 서버를 늘리면 내용이 따로 논다는 것이고, 그땐 store.js부터 여러 서버가 함께 쓰는 DB로 옮겨 고치고, 이어서 쿠키 보안과 요청 횟수 제한을 넣겠습니다.

변형 문장: 장애를 물으면 한계 앞에 "저장이 실패하면 오류를 돌려주고 이전 결과는 그대로 둡니다"를 넣는다. 못 본 걸 봤다고 하지 않는다.

예시 문항(가상 과제): 프로덕션에 배포하기 전에 무엇을 고려해야 합니까?

예시 답안(가상 과제): 제 구현은 배포 대비로 세 가지는 했고, 여러 서버가 함께 쓰는 DB와 쿠키 보안, 요청 횟수 제한, 데모 계정 끄기는 아직 남았습니다. 한 것은 시각을 한국 시간으로 고정했고, 설정 없이도 기본값으로 뜨게 했고, 상태 확인 경로를 두었습니다. 이유는 휴직과 퇴직을 가르는 날짜 판단이 서버 시계에 따라 하루 밀리면 안 되고, 처음 받는 사람이 바로 띄워 봐야 하기 때문입니다. 확인은 서버 시계와 상관없이 한국 시각이 나오는 시각 테스트를 포함해 테스트 21개가 모두 통과한 것과, 설정 없이 띄워 상태 확인이 정상인 것을 본 것으로 했습니다. 도커는 환경에 없어 돌리지 못했고 기록에 건너뜀으로 남겼습니다. 한계는 저장이 서버 한 대의 파일이라 서버를 늘리면 내용이 따로 논다는 것이고, 그땐 store.js부터 여러 서버가 함께 쓰는 DB로 옮겨 고치고, 이어서 쿠키 보안과 요청 횟수 제한을 넣겠습니다.

### F. 핵심 동작과 확인한 방법 (틀 F, D1 근거 + 세 겹 확인)
뼈대: 기능 하나 → 기준값이 결과를 가르는 지점 → 세 겹으로 확인(테스트·직접 호출과 입력 대조·화면) → 건수 검산 → 핵심 계산에서 테스트로 못 고정한 경우

외울 답: 제 구현은 `[기능 하나]`가 핵심이고, 세 겹으로 확인했습니다. 이유는 담당자 기준 `[④]`이 결과를 가르는 지점이라 계산을 떼어 따로 봐야 했기 때문입니다. 첫째, 테스트 `[①]`개가 모두 통과했고 그중 하나는 기준값과 딱 같은 경계입니다. 둘째, 서버를 띄워 `[기능]`을 직접 불러 200을 받고, `[첫 결과]`가 맞는지 입력과 맞춰 봤습니다. 셋째, 화면에서도 같은 결과를 봤습니다. 건수도 들어온 `[②]`건이 쓴 건수와 버린 건수의 합과 맞았습니다. 한계는 `[핵심 계산에서 테스트로 못 고정한 경우]`이고, 그땐 `[그 테스트]`부터 넣겠습니다.

변형 문장: AI에게 시킨 것·바꾼 것·도구를 물으면 틀 C로 쓴다. 확인 못 한 것을 물으면 "그건 확인하지 않았습니다. 확인하려면 `[어느 기록]`을 보면 됩니다"로 한계 문장을 대신한다.

예시 문항(가상 과제): 핵심 동작은 무엇이고 어떻게 확인했습니까?

예시 답안(가상 과제): 제 구현은 먼 사람부터 자리를 주는 거리 우선 배정이 핵심이고, 세 겹으로 확인했습니다. 이유는 400m 기준이 결과를 가르는 지점이라 계산을 떼어 따로 봐야 했기 때문입니다. 첫째, 테스트 21개가 모두 통과했고 그중 하나는 딱 400m인 경계입니다. 둘째, 서버를 띄워 배정을 직접 불러 200을 받고, 첫 자리가 가장 먼 사람인지 입력과 맞춰 봤습니다. 셋째, 화면에서도 같은 결과를 봤습니다. 건수도 신청 310건이 쓴 294건과 버린 16건의 합과 맞았습니다. 한계는 거리가 같은 두 사람의 순서를 테스트로 고정하지 않은 것이고, 그땐 그 경우의 테스트부터 넣겠습니다.

## 네 마디 골격 (40초)
```
시작  "제 구현은 X입니다."                  ← 모듈 이름
이유  "이유는 Y이기 때문입니다."             ← 담당자 기준
확인  "확인은 Z로 했습니다."                 ← 숫자 2~3개
한계  "한계는 W이고, 그땐 V부터 고치겠습니다."  ← 신뢰
```
- 질문의 전제가 내 구현과 다르면 차이를 먼저 밝힌다: "질문의 전제 …는 제 구현과 다릅니다, 실제로는 …".
- 3분쯤 핵심을 먼저 적고 나머지를 보강한다. "더 확인해야 합니다"로 끝내지 않는다 — "확인하려면 A(파일·명령)를 보면 됩니다".

## 세 가지 금지
| 금지 | 대신 |
