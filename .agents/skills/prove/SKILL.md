고치는 파일: out/prove_*.json · out/prove.md · 비교 실행 스크립트(scripts/prove_*) 셋뿐. 과제 코드·원본 데이터는 읽기만 한다.

> 사용자가 명령 뒤에 붙인 문장(줄글이어도 된다 — 그 안의 목적·근거·범위·하지 마라·내 판단·확인)은 이 파일의 지시보다 우선한다(고치는 파일 범위와 "멈춰라"는 그대로). 보고 첫 줄에 "이번 목적: …"을 붙인 문장에서 한 줄로 옮기고, 붙인 문장이 없으면 리스크 칸에 "[목적 줄 없음]"이라고 적는다.

# $prove — 기준안·하한·우리 안 비교 (S4 끝 · S6 $defend 앞)

## 할 일
1. 지표는 PLAN "성공 기준"에서 1~2개를 가져온다(단위 포함). 성공 기준에 숫자 지표가 없으면 "어떤 숫자로 좋고 나쁨을 잴까요? 하나만 정해 주세요"라고 사용자에게 1개만 묻고 멈춘다.
2. 행마다 실행 스크립트를 scripts/prove_<종류>.*로 두고 **실제로 실행**한다. 종류는 baseline(가장 단순한 기준안) · lower_bound(이론 하한, 계산식 1줄을 desc에) · ours(지금 코드의 결과를 그대로 부른다 — 다시 짜지 않는다) · current(제공 데이터에 현재 운영 기록이 있을 때만).
3. 스크립트마다 결과를 out/prove_<종류>.json에 이 모양으로 쓴다: `{"method": "기준안", "desc": "설명 1줄", "metrics": {"지표(단위)": 숫자, …}, "vs_lower_pct": 숫자, "command": "실행한 명령"}`. vs_lower_pct는 스크립트가 계산한다(하한 행은 100).
4. `cp /tmp/harness/templates/dev/PROVE.md out/prove.md`(없을 때만) → `node /tmp/harness/scripts/prove_table.mjs` 를 실행해 표를 json에서 채우고 대조 결과를 붙인다. **표 숫자를 손으로 쓰거나 고치지 않는다.** "불일치"가 나오면 json을 다시 만들고 다시 돌린다.
5. "왜 이 기준인가" 2줄과 "깨지는 조건" 3줄은 근거(PLAN·담당자 답 시각·out 파일)와 함께 초안으로 쓴다.
6. 반증 리뷰는 직접 하지 않는다. 아래 문구를 그대로 출력해 사용자가 새 터미널 codex에 붙이게 한다:
   `너는 반증 리뷰어다. out/prove.md·out/prove_*.json·코드만 읽어라. 이 비교의 숫자가 틀렸을 수 있는 이유 3개(기준안이 일부러 약한가·하한 계산이 맞나·우리 안이 같은 입력을 썼나 등)를 찾고, 각각 확인 명령을 돌려 결과를 VERIFY.md에 V-번호로 지적만 적어라. 아무 파일도 고치지 마라.`
7. 결과 숫자는 HOW_TO_RUN "설계 기준과 최적화 방식"과 `$defend`의 "숫자"·"기준과 이유" 장 재료다 — 거기에 옮길 문장 한 줄을 보고에 넣는다(옮기는 건 그 파일 담당이 한다).
8. 역할 카드 D(데이터·측정 탭)로 일하는 세션이면 커밋하지 말고 "커밋 준비됨: out/prove.md out/prove_*.json scripts/prove_*"로 끝낸다. 혼자면 `[S n/6] 효과 비교 기준안 대비 n%` 로 커밋한다.

## 하지 않는 것
표 숫자 손계산·손수정 / 기준안을 일부러 약하게 만들기 / 우리 안을 비교용으로 다시 구현하기 / 반증 리뷰를 같은 세션이 하기 / 원본 데이터 수정.

## 끝 조건
out/prove.md 표의 숫자가 `prove_table.mjs` 대조에서 "일치"이고, 반증 리뷰 문구가 화면에 있다.
