고치는 파일: PLAN.md · REQUIREMENTS.md의 '만들 것/안 만들 것' 칸 초안. 다른 파일은 읽기만 한다.

> 사용자가 명령 뒤에 붙인 목적·범위·하지 마라·내 판단·확인 줄은 이 파일의 지시보다 우선한다(고치는 파일 범위와 "멈춰라"는 그대로). 보고 첫 줄에 "이번 목적: …"을 그 문장 그대로 옮기고, 붙인 줄이 없으면 리스크 칸에 "[목적 줄 없음]"이라고 적는다.

# $plan — PLAN과 확인 DM (S2 끝, ~48분)

## 할 일
1. 근거는 둘뿐이다: LOG '담당자 대화'의 답 원문(시각 포함)과 README·REQUIREMENTS 원문. 근거 없는 칸은 "미확인".
2. PLAN 7칸을 채운다: 문제 / 사용자 / 성공 기준(지금 값 → 목표 값, 측정 방법) / 만들 것 / 안 만들 것 / 가정 / 한계.
3. REQUIREMENTS의 **모든 행**을 '만들 것/안 만들 것' 칸에서 둘 중 하나로 정한다. 빠진 번호가 0개여야 한다. 안 만들 것에는 사유(시간·근거 없음·README 제외 범위)를 쓴다. 만들 것 중 이번 회차 구현 순서 상위 3개에 ★를 단다(★1이 핵심 계산 — `$defend`가 규칙 한 문장을 여기서 뽑는다). 이미 사람이 적은 칸은 바꾸지 않는다. 서로 동시에 성립할 수 없는 행이 있으면 두 행 번호와 이유를 보고 끝에 '충돌:' 줄로 적는다 — 어느 쪽을 먼저 지킬지는 사람이 DECISIONS D7에 정한다.
4. 같은 요구를 푸는 방법이 둘이면 더 단순한 쪽을 만들 것에, 더 정교한 쪽은 PLAN 한계에 "대안(D1 대안): …"으로 적는다.
5. 담당자 답이 두 뜻이면 놓치면 비싼 쪽으로 잠정하고 PLAN 가정에 "잠정 — 확인 필요"로 적는다.
   PLAN '요구 목록' 표의 `줄기`·`묶음` 열을 채운다. 요구(R) 행이 8개 이하면 두 열 다 "—"이고 '소유 파일 분할'은 "단일 줄기" 한 줄. 9개 이상일 때만 나눈다: 같은 모듈 2~3행을 같은 묶음 번호로(모듈 1개면 분할 없음), `줄기`는 A 또는 A2, 뼈대가 주는 행은 `줄기=확인만`. 표 아래 '소유 파일 분할' 절에 `A: server.js · src/<모듈A>* · tests/feat_<모듈A>* · 공용 문서 / A2: src/<모듈B>* · tests/feat_<모듈B>*`. 같은 파일을 두 줄기에 넣지 않는다.
6. PLAN 표 아래 `- 뼈대 부품:` 줄에 깔 부품을 `auth,store,lock,schema,docker` 중 쉼표로 쓴다 — `$s1`의 '뼈대 추천' 중 README 근거 줄이 있고 만들 것에 든 행이 쓰는 것만, 하나도 없으면 `없음`. S3에서 `bootstrap.mjs --scaffold node-v2 --with plan`이 이 줄을 그대로 읽는다.
   PLAN '## 데이터 처리 규칙' 절의 표에(위 '요구 목록' 표가 아니라 그 절의 4칸 표에) inventory 항목마다 처리 한 줄과 근거(담당자 시각·README 줄)를 적는다.
7. 담당자에게 보낼 확인 DM을 _playbook/ASK.md의 합의 확인 형식으로 5줄 이내, 기술 용어 없이 보여 준다.
8. 커밋하지 않는다. 담당자가 "맞다"고 하면 사용자가 "기록만 해라: … '확인 받은 시각: HH:MM'"으로 [S 2/6]을 커밋시킨다.

## 끝 조건
PLAN 7칸이 채워지고(근거 없으면 "미확인"), REQUIREMENTS의 만들 것/안 만들 것 칸에 빈 행이 0개이고, 확인 DM이 화면에 있다.
