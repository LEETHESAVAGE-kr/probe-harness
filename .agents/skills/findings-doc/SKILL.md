# findings-doc — 출처 대조 → FINDINGS 작성

## 입력과 전제
- uploads/(원본, 수정 금지), portal/(사람이 옮긴 포털 값 — 옮긴 방법·시각이 SOURCE_MATRIX 머리에 있어야 한다), INTERVIEW.md(담당자 말 원문·시각), AGREEMENT.md(무엇을 믿을지 우선순위).
- portal/ 파일이 포털 화면의 건수·합계와 대조되지 않았으면 먼저 그 대조(out/portal_check.md)부터 한다. 대조 안 된 파일은 근거로 쓰지 않는다.

## 절차
1. **키 정하기**: 세 출처를 이을 키(작업번호·장비ID·사번 등)와 비교할 값(상태·날짜·수량·금액)을 정해 SOURCE_MATRIX 항목으로 적는다. 키 표기를 정규화(공백·대소문자·하이픈·앞자리 0)하면 1순위 규칙대로 전후 건수 비교표를 out/changes_log.md에 남긴다.
2. **check.py로 대조**(표준 라이브러리 csv, 출력 utf-8, out/에만 쓰기): 키별 `양쪽 다 / 파일만 / 포털만`과 **칸마다**(상태·날짜·숫자) 같음/다름, 양쪽 값을 out/source_compare.csv에, 건수를 out/summary.md에. 결론(예: 초과 여부)만 비교하지 않는다 — 결론만 보면 값이 다른 칸이 가려진다. 실행 출력 마지막 줄 = `rows_in / used / excluded(사유별) / 상태별 건수`.
3. **담당자 말 겹치기**: INTERVIEW에서 기준·정의·예외(예: "완료의 뜻", "주기 변경", "제외 대상")를 SOURCE_MATRIX '담당자 말' 칸에 시각과 함께. 담당자 말이 파일·포털과 다르면 그것도 불일치다.
4. **FINDINGS 쓰기**: 불일치마다 한 행. 중요한 것(결론 숫자를 바꾸는 것)부터.
   | # | 무엇 | 어디서 어긋남 (출처 A vs 출처 B) | 왜 중요 | 누구에게 확인 | 권고 | 확인한 숫자 (out/ 근거) |
   - **확인한 숫자** 칸은 out/ 파일의 건수·합계·차이를 그대로 옮기고 파일명을 단다. 지금 확인한 것과 남은 확인을 나눠 쓴다. "더 확인이 필요하다"만으로 끝내지 않는다.
   - **왜 중요**는 결론에 주는 영향을 숫자로(예: "지표 a% → b%").
   - **누구에게 확인**은 역할로(담당 부서·역할). 권고는 한 문장 행동.
   - **안전·규정 위반은 맨 위**: 수량·상태 대조가 '일치'여도 README·기준 문서의 조건으로 한 번 더 거른다.
   - 결론에 영향 없는 어긋남은 '참고'로 내린다.
5. **자기 대조**: FINDINGS의 숫자를 out/ 파일과 하나씩 맞춰 보고(건수만 세지 말고 값까지), 안 맞으면 그 행만 고친다. 결론 숫자는 verify.py로 check.py 없이 원본에서 다시 세고, 규칙 하나를 일부러 깨서 잡히는지 본다. 결과를 VERIFY.md에 행으로 남긴다(사람 문서 — 스크립트가 덮어쓰지 않는다).
6. **결론은 REPORT.md에**: 결론 숫자·목표 대비·기준을 바꾸면 달라지는 숫자(민감도)·남은 확인(FINDINGS 번호).

## 흔한 어긋남 체크 (데이터에서 실제로 세어 본다)
같은 대상의 표기 차이(ID·이름) / 한쪽에만 있는 건(폐기·취소가 남음) / 상태 정의 차이("완료"가 마감인지 실제 수행인지) / 날짜 기준 차이(계획일·수행일·등록일) / 중복 입력(id만 다른 같은 내용) / 단위 차이 / 기준값이 최근에 바뀜(문서·마스터가 낡음) / 필터 걸린 채 옮긴 포털 화면.

## 하지 않는 것
uploads 원본 수정 / 추측으로 칸 채우기(모르면 "미확인") / 사람 확인 없이 '근거 우선순위' 결정 / 전체 재작성(틀린 행만 고친다).
