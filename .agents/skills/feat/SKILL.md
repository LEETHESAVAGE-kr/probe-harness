고치는 파일: 이번 행에 필요한 코드(server.js · src/ · public/) · tests/feat_<기능>.test.* · REQUIREMENTS.md 그 행의 파일·테스트·상태 칸 · LOG.md 본표 한 행 · LOG.md "## 설명 카드" 카드 한 장. 그 밖은 읽기만 한다.

> 사용자가 명령 뒤에 붙인 목적·범위·하지 마라·내 판단·확인 줄은 이 파일의 지시보다 우선한다(고치는 파일 범위와 "멈춰라"는 그대로). 보고 첫 줄에 "이번 목적: …"을 그 문장 그대로 옮기고, 붙인 줄이 없으면 리스크 칸에 "[목적 줄 없음]"이라고 적는다.

# $feat — 기능 하나 (S4, 55~150분)

## 1. 고르기·세 줄 계획 (먼저 말하고 진행)
- REQUIREMENTS에서 '만들 것'이고 상태 칸이 빈 **첫 행 하나**만 고른다. 행 번호와 원문을 한 줄로.
- 세 줄: ① 범위와 고칠 파일 ② 테스트 3개 이름(정상 / 경계: 담당자 기준값과 딱 같은 값 / 오류: 없는 ID·빈 값) ③ 끝 조건. 그리고 한 줄 더: 이 기능이 쓰는 시그니처 슬롯(D1~D6, 없으면 "없음").
- 시그니처 슬롯: D1 단순 규칙 먼저 · D2 쓰기 직렬화·읽기 스냅샷 · D3 입력=사용+버림 검산 · D4 업무 시간대·설정 기본값 · D5 스키마 파일에서 키를 읽어 대조 · D6 진입점→인증→검증→계산→저장→응답. README가 요구하지 않는 부품을 슬롯 때문에 넣지 않는다.
- 더 단순한 방법이 있으면 그것을 만든다. 더 정교한 방법은 PLAN 한계에 "대안: …"으로 남길 문장만 준비한다.

## 2. 테스트 → 구현
- 테스트 3개를 tests/feat_<기능>.test.*에 먼저 쓰고 실패하는 것을 본다(실패 출력 1줄을 붙인다). 테스트 이름 앞에 슬롯을 단다: `test("[D1] …")`. 슬롯을 쓰는 함수 머리에 주석 한 줄 `// [Dn] …`.
- 구현은 고칠 곳만. 요구 밖 기능·새 패키지·전체 재작성 금지. 데이터를 빼·바꾸·합치면 먼저 changes_log 행(D에게 요청).
- 이번 테스트를 돌려 통과 n·실패 n을 붙인다. out/test_result.txt도 네가 갱신한다(S6엔 B가 다시 쓴다).

## 3. 4문장 퀴즈 — 커밋 전 반드시
- 코드와 대조해 이 기능을 설명하는 문장 4개(1 무엇을 / 2 어떤 순서로 / 3 왜 그렇게 / 4 어디서 틀리나)를 만들고, 문장마다 A/B 두 판을 낸다 — 하나는 코드와 맞고 하나는 미묘하게 틀리다(순서·경계·포함/제외·숫자 중 하나만 바꾼다). 맞는 판의 자리(A/B)는 문장마다 섞는다. 정답은 말하지 않는다.
- 형식: `1A …` / `1B …` / `2A …` … 여덟 줄. 끝 줄에 "1A 2B 3A 4B처럼 답해라"라고 쓰고 멈춘다.
- 사용자가 답하면 틀린 고름 수를 센다. 틀린 고름이 **2개 이상**이면 커밋하지 않는다. 틀린 번호와 맞는 판을 보여 주고 선택지 둘만: (가) 단순화 — 무엇을 빼면 맞는 판이 쉬워지나 / (나) 제외 — REQUIREMENTS 그 행을 "안 만듦 — 설명 불가"로. 그리고 멈춘다.
- 틀린 고름이 1개 이하면 4로.

## 4. 기록·커밋
- REQUIREMENTS 그 행: 파일(파일:함수), 테스트(이름 3개), 상태(`됨 [S 4/6]`).
- LOG "## 설명 카드"에 카드 한 장, 5줄 이하:
  `### 카드 n — <기능>` / `- 파일·함수: …` / `- 근거: 담당자 답 HH:MM 또는 README 줄` / `- 테스트: 이름 3개 · 통과 n/n` / `- 바로잡은 것: 내가 고치거나 거부한 Codex 제안(없으면 "없음")` / `- 기법: D1·D3`(쓴 슬롯) / `- 약점: 어떤 조건에서 얼마나(숫자)` / `- 내 4문장: 맞는 판 네 문장 (퀴즈 정답 n/4)`
- LOG 본표 한 행. `[S 4/6] R<번호> <한 줄> (Dn <기법 이름>)` 로 커밋하고(괄호에 쓴 슬롯, 없으면 괄호 생략) `git show --stat HEAD`를 붙인다. 역할 카드 B·C·D 세션이면 커밋하지 말고 "커밋 준비됨: 파일 목록"으로 끝낸다.

## 묶음 모드 — 범위 줄에 `묶음: R3 R4 R5`가 있을 때만 (없으면 이 절을 통째로 건너뛴다)
- 조건: 같은 모듈(소유 파일이 겹치는 행)만, 최대 3행. 어긋나면 만들지 말고 보고의 "이번 목적" 바로 다음 줄에 이 문구 그대로 `묶음 불가: R5는 다른 모듈 — 따로 쳐라`(R번호만 바꾼다)를 쓰고 멈춘다.
- 행마다 순서대로 세 줄 계획 · 테스트 1개 이상 · 구현. 경계 테스트는 묶음 전체에서 1개 이상.
- 퀴즈는 **묶음당 한 번**: 네 문장이 묶음 전체를 아우르고 문장마다 어느 R인지 표시한다(생략 불가). 틀린 고름 규칙은 같다.
- 설명 카드는 **행마다 1장**, REQUIREMENTS 상태 칸도 행마다. 커밋은 묶음당 1회 `[S 4/6] R3-R5 <한 줄> (Dn)`.
- 보고 첫 줄에 경과 분을 쓴다: `이번 목적: … · n분 경과 · 12분 상한`.
- 묶음 안 한 행에서 테스트가 실패하면 그 행만 되돌리고(`git checkout -- 그 파일`) 나머지 행으로 커밋한 뒤 보고에 `R4 실패 — A2로` 한 줄.

## 끝 조건
테스트 3개 통과(얇게 구간은 최소 동작 1 + 테스트 1, 경계 1개는 반드시), REQUIREMENTS 그 행의 상태 칸이 채워짐, 설명 카드 한 장 — 요구마다 설명 카드 1장(총 = 만들 것 행 수), 커밋(또는 틀린 고름 2개 이상으로 멈춤).

## 보고 (5줄)
한 일 / 검증: 테스트 통과 n·실패 n(명령) / 왜 이 방식인가 1줄(쉬운 말) / 리스크: 카드의 약점(바로잡은 것이 "없음"이면 `[거부 기록 0건]`도) / 다음: "`$feat` 다음 행".
그 아래 한 줄: `DECISIONS Dn 후보: 결정 … / 대안(더 단순·더 정교) … / 약점 … / 검증 …` — DECISIONS에는 사람이 옮긴다.
