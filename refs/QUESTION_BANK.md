# QUESTION_BANK — 질문 뱅크 (평소엔 안 연다 · 시험 중엔 ASK.md·DEFEND.md가 먼저)

## A. 담당자 질문 — 전체 순서와 데이터 질문 (ASK.md의 확장판)
### A-1. 순서 (○○ = 이 과제의 결과물·업무, △△ = 담당자가 쓴 모호한 말, ×× = 뺄 후보)
```
[지도]   제가 이 업무를 잘 몰라서요. 어떤 걸 여쭤보면 도움이 될까요?               ← 맨 먼저
[장면]   가장 최근에 ○○하셨던 날, 처음부터 끝까지 어떻게 진행됐나요?
[왜]     그 일이 제대로 안 되면 어떻게 되나요? 누가, 얼마나 손해인가요?
[지금]   지금은 어떻게 처리하세요? 엑셀? 수작업? 누가, 얼마나 걸려서?
[기준]   좋은 ○○와 아쉬운 ○○를 어떻게 구분하세요? 가장 먼저 보시는 건요?
[순서]   의견을 주실 때 어떤 순서로 말씀하세요? 한 번에 몇 가지까지 짚으세요?
[문장]   그때 실제로 하신 말을 문장 그대로 기억하세요?
[모호어] '△△'라고 하셨는데 ⓐ인지 ⓑ인지 ⓒ인지 어느 쪽에 가까울까요?
[정량]   얼마나 자주, 한 번에 몇 건, 몇 명이 쓰나요? 틀리면 무엇이 얼마나 비싼가요?
[경계]   빼야 하는 경우가 있나요? 예외는요? 동률·중복·취소는 어떻게 하세요? 기준값과 딱 같으면 통과인가요?
[민감]   공개하면 안 되는 이름·번호·금액이 있나요?
[기준일] 최근 바뀐 요구나 날짜 붙은 기준(문서·마스터·규정)이 있나요? 지금도 맞나요?
[성공]   이게 잘 됐다는 건 무엇을 보고 아실 것 같으세요? 숫자로 말하면요? 지금 값은요?
[거절]   만약 ××는 없고 ○○만 된다면 업무에 쓸 만하실까요?                        ← 마지막 (범위 축소 사전 동의)
[정리]   정리하면 ○○·△△·×× 세 가지가 핵심이라고 이해했는데 맞을까요?            ← [거절]까지 다 돈 뒤, 내가 고른 셋을 확인받는다
```
- [정리]는 "기능 3개 골라 주세요"의 대체다 — 담당자에게 고르게 하지 않고, 장면·기준·숫자에서 **내가 추린 셋**을 인용 형태로 확인받는다. 이 답이 PLAN '만들 것'의 근거가 된다.
- [기준]→[순서]→[문장]은 **연속으로**, 주제를 바꾸지 않고 같은 자리를 세 번 판다(가장 수익이 큰 구간). [순서]의 "n개까지"는 그대로 성공 기준·출력 형식이 된다.
- 셀 수 있는 것("너무 많다/길다", "○○면 아예 안 된다")은 고정 코드 판정으로, "○○가 들어가야 한다" 같은 의미 판단만 LLM에 — "왜 이렇게 나눴나"의 준비된 답.
- 답을 받은 뒤 같은 자리를 더 파는 5수: 극단("제일 심했던 경우는?") · 반례("잘 됐던 때는 뭐가 달랐나요?") · 문장 그대로 · 빈도("10번 중 몇 번쯤?") · 거절 확인.

### A-2. 데이터가 있으면 (inventory에서 센 것을 그대로 묻는다)
- 이 열(코드값·위치·상태값)은 무슨 뜻이고 단위는요? 그중 대상인 것은요?
- 빈 값·이상한 값(-1·9999)은 무엇을 뜻하나요?
- "같은 행이 {n}건 두 번 들어 있습니다 / id만 다른 같은 내용이 {n}건 / 처음 보는 코드 {값} — 어떻게 처리할까요?"
- 이 데이터에 없는데 판단에 쓰시는 정보가 있나요?

### A-3. 보내지 않는 문장
| 보내지 않는다 | 대신 |
|---|---|
| "해야 할 일/기능 1,2,3 알려 주세요" | [지도] → [장면] |
| "어떻게 할까요?" | 선택지 2개 + 추천 |
| "그건 어려울 것 같습니다" | 빼는 이유 + "기록해 두겠습니다" |
| "어떤 식으로 만들면 될까요?" | "방법은 제가 찾겠습니다. '이건 됐다' 싶은 상태만 알려 주세요" |
| 모델·스키마·엔드포인트 같은 기술 용어 | 담당자가 화면에서 보는 것으로 |
| 답을 기다리며 멈추기 | 보내고 바로 다음 항목 |

## B. 서술형 예상 질문 22개

### B-의도 — 가장 많이 나온다
1. 사용자는 누구고, 어떤 결정을 개선하나?
2. 반드시 지킬 조건과 점수로 조정할 것을 어떻게 나눴나? 왜?
3. 문제에 없는 것 중 무엇을 가정했나? 그 가정이 틀리면 무엇이 깨지나?
4. 하지 않기로 한 것은 무엇이고 왜인가?
5. Codex에게 무엇을 시켰고 무엇을 직접 했나? 그 경계를 어떻게 정했나? → LOG 고정 절
6. Codex 출력을 어디서 믿지 않았나? 어떻게 검증했나?
7. 작업을 어떻게 쪼갰나? 왜 그 단위였나? → S1~S6, 기능별 커밋
8. 중간에 방향을 바꾼 적이 있나? 무엇을 보고 바꿨나? → DECISIONS, 요구 변경 커밋
### B-기술
9. 실제로 어디서 어떻게 실행되나? 명령 한 줄로. → README_RUN
10. 같은 입력에 같은 출력이 나오는 것을 어떻게 보장하나? 동률(tie-break) 처리는?
11. 예외·실패 상황에서 어떻게 되나? 사용자가 그것을 아나?
12. 비밀정보·개인정보를 어떻게 다뤘나?
13. 데이터가 10배 오면 어디가 먼저 무너지나? 여러 사람이 동시에 쓰면?
14. 이 구조를 고른 이유는? 더 단순한 대안은 왜 부족했나?
15. 테스트가 실패하는 것을 직접 본 적이 있나? 어떤 테스트였나?
### B-인지 — 전원이 가장 낮았던 축
16. 가장 약한 부분은 어디인가? → PLAN 한계·DECISIONS 약점
17. 어떤 입력에서 틀린 답을 내나? 하나만 구체적으로.
18. 지금 코드에서 설명 못 하는 줄이 있나? 백엔드 파일들이 어떻게 연결되나(요청 → 응답 경로)?
19. 다시 한다면 무엇을 다르게 하겠나?
20. 시간이 2배 있었다면 무엇을 했겠나? 왜 그게 우선인가?
21. 이 지표가 실제 업무 목표와 어떻게 이어지나? → PLAN 성공 기준
22. 내일 실무에 넣는다면 무엇을 먼저 확인해야 하나? 프로덕션 배포 전 고려사항은?

## C. 컴포넌트 용어 카드 ("구조·연결을 설명하라" 유형)
| 용어 | 뜻 | 보통 어느 파일 |
|---|---|---|
| 로더/파서 | 입력(CSV·요청)을 읽어 구조로 바꾼다 | datasets·store |
| **검증기(validator)** | 입력이 규칙에 맞는지(필수 열·없는 ID·형식) 확인, 틀리면 거절 | datasets |
| **생성기(creator/planner)** | 핵심 계산·결과 생성 | 계산 모듈(planner·scorer 등) |
| **결과 검증기(plan check)** | 생성 결과가 운영 규칙을 지켰는지 다시 센다 | export의 violations |
| 저장소(store) | DB 읽기·쓰기, 영속 | store / sqlite |
| 핸들러/라우터 | 요청 → 위 컴포넌트 호출 → 응답 | server |
+ 두 단어: **동기**(요청이 계산 끝날 때까지 기다림 — 대부분 이렇게 만들었다) / **비동기·별도 프로세스**(요청은 바로 "진행 중" 응답, 계산은 뒤에서 — 안 했으면 "안 했다, 재계산 중 다른 요청이 기다린다, 먼저 바꿀 곳은 POST 핸들러에 잠금+작업 ID").

## D. 미리 문장으로 써 둘 답변 3개 (S6 끝나면 아래 빈칸을 채워 LOG 끝에 적는다 — 서술형 때 그대로 떠올린다)
