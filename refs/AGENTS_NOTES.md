# AGENTS_NOTES — AGENTS.md 규칙 12줄의 줄별 해설 (v2.1 원문 그대로 옮김)

> v2.2에서 AGENTS.md는 규칙 12줄·도구 표·명령 표만 남기고, 아래 해설을 여기로 옮겼다. 작업 폴더에는 깔리지 않는다(bootstrap이 복사하지 않음) — 필요할 때만 `/tmp/harness/refs/AGENTS_NOTES.md`를 연다.
> 아래는 v2.1 문장을 고치지 않고 옮긴 것이다. v2.2에서 바뀐 규칙 줄(3·6·9·10줄)의 해설 중 6줄 PLAN '만들 것'의 개수 상한, "질문 초안(10줄)", "PLAN 확인을 받기 전에 초안의 질문을 전부 보낸다"는 지금 규칙과 다르다 — 지금 뜻은 AGENTS.md 규칙 블록과 `.agents/skills/*/SKILL.md`가 정한다.

## 풀어 쓴 설명 (줄 번호 = 위 규칙의 줄)

### 1줄 — 역할·다시 읽기·승인
- 너는 구현을 맡고, 나는 무엇을 풀지·맞았는지를 책임진다. 판단이 갈리면 멈추고 묻는다.
- 이 파일은 대화 시작 때 이미 들어 있다. 규칙이 흐려졌다고 내가 말할 때(`AGENTS.md를 따라:`)만 다시 읽는다(토큰 사용량도 평가된다).
- 파일 삭제·기존 파일 덮어쓰기·패키지 설치는 무엇을 왜 하는지 한 줄로 말하고 내 승인을 받은 뒤 한다. 과제 README.md와 제공된 데이터(uploads/ 등)는 덮어쓰지 않는다.

### 2줄 — 하나
- 지시 하나 = 범위 하나 + 출력 파일 하나. 지시에 범위나 출력 파일이 없으면 한 번만 되묻는다.
- 내가 `$명령` 뒤에 붙이는 4줄(목적·근거 / 범위·하지 마라·고칠 파일 / 내 판단·이유 / 확인)이 그 지시의 범위다. "하지 마라"에 적은 것은 좋아 보여도 만들지 않는다.
- 코드를 쓰기 전에 (a) 이번 범위 (b) 끝 조건 (c) 건드리지 않을 파일을 먼저 말한다.
- 고칠 곳만 고친다. 전체 재작성·요구되지 않은 기능·새 프레임워크·대규모 리팩터링은 하지 않는다.
- 단계가 끝나면 테스트를 돌리고, 통과한 뒤 커밋하고, 멈춰서 보고한다. 커밋은 `[S n/6] 한 줄` + 본문 3줄(드리프트: 합의에서 벗어난 것 / 증거: 테스트 없이 "된다"고 한 것 / 의심: 너무 순조로웠다면 무엇을 안 봤나). 커밋 뒤 `git show --stat HEAD`로 파일이 실제로 들어갔는지 본다.

### 3줄 — 증거
- "완료"라고 말할 때는 실행한 명령과 출력(통과 n·실패 n)을 그대로 붙인다. 실행하지 않은 것은 "미검증"이라고 쓴다.
- 에이전트(나 포함)가 "됐다"고 하면 `git diff --stat`과 테스트 출력 숫자로만 믿는다. 통과 0은 통과가 아니다.
- 문서(PLAN·LOG·DECISIONS·README_RUN·커밋 메시지)에 쓰는 숫자는 out/에 남는 실행 결과에서만 가져온다. 기억이나 손계산으로 쓰지 않는다. 실행마다 바뀌는 값(소요 시간·시각)은 범위와 기준 커밋으로 적는다.
- 실패를 숨기는 try/except, 테스트를 통과시키려고 기대값을 바꾸는 것은 금지. 요구가 바뀌어 기대값을 바꿀 때는 테스트에 "요구 변경(시각)·이전 기대값" 주석을 단다.
- 기능이 끝나면 내가 쉬운 말 4문장으로 설명한 것을 코드와 대조해 틀린 곳만 짚는다. 내가 설명 못 하는 방식은 더 단순한 방식으로 바꾸고, 원래 방식은 PLAN 한계에 '대안'으로 적는다. 더 단순한 방법이 있으면 그것을 먼저 만든다.
- 매 보고 형식: 한 일 1~3줄 / 검증(명령·출력, PASS·FAIL·미검증·내가 확인) / **왜 이렇게 했나 1~2줄(쉬운 말로 — 서술형에서 내가 직접 설명한다)** / 리스크 1줄 / 다음 1줄. 설명 못 할 코드는 쓰지 않는다.
- 새 테스트는 먼저 실패하는 것을 보고 통과시킨다(실패를 본 적 없는 테스트는 믿지 않는다). 판정 코드는 같은 입력에 같은 출력(동률 처리 규칙 포함)을 테스트 1개로 고정한다.

### 4줄 — 전후
- 데이터를 빼거나(빈 행·중복·취소분), 바꾸거나(단위·표기·코드 정규화), 합치면(병합·집계) **처리 전에** out/changes_log.md에 한 행을 쌓는다:
  `| 단계 | 처리(무엇을 왜) | 전 건수 | 후 건수 | 전 합계 | 후 합계 | 차이 | 결론을 바꾸나 |`
  (`node /tmp/harness/scripts/changes_log.mjs`가 이 행을 계산해 붙인다 — 처리 전에는 예상 숫자(`--before-count`·`--after-count`, 결론 칸 "예상")로 한 행, 처리 뒤에는 전후 파일로 실제 행. 행은 남기고 값만 비우는 처리는 `--cells 열`로 칸 수를 센다. "결론을 바꾸나" 칸은 결론 숫자를 처리 전후로 한 번씩 돌려 본 뒤 채운다.)
- 코드도 같다: 입력 n = 사용 m + 버림 k(사유별)를 실행 출력에 남기고, 이 등식을 테스트로 확인한다. 숫자가 안 맞으면 완료가 아니다.
- 입력=사용+버림 검산은 같은 행이 두 번 들어간 경우(완전 중복)를 못 잡는다. S1 inventory의 완전 중복 수를 보고 처리 규칙을 따로 정한다.
- "더 확인해야 한다"로 끝내지 않는다. 지금 셀 수 있는 것은 세고, 못 하는 것은 누가 무엇으로 확인할지 적는다.
- 외부 코드(공개 저장소·예제)를 빌리면 출처 URL·라이선스·가져온 범위(함수·파일)를 LOG에 적는다. 결과물을 통째로 외부 코드로 바꾸지 않는다.

### 5줄 — 서버
- 런타임 순서: 과제가 정한 언어·프레임워크 → 없으면 node 내장 `http`(의존성 0) → node가 없으면 python `http.server`.
- 주소는 `0.0.0.0`(localhost만 열면 미리보기 도구가 못 붙는다), 포트는 `PORT` 환경변수(기본 3000). 포트가 차 있으면 다른 포트로 띄운다.
- 서버를 끌 때는 내가 띄운 프로세스(PID)만 끈다. 남의 프로세스는 종료하지 않는다.
- 시작 명령·테스트 명령·포트는 README_RUN.md에 적는다. 뼈대가 필요하면 `/tmp/harness/scaffold/node/`(또는 `python/`)를 참고하고 출처를 LOG에.

### 6줄 — PLAN (7칸)
- 문제 / 사용자 / 성공 기준(지금 값 → 목표 값, 측정할 숫자) / 만들 것(3개 이하, README 요구 번호를 단다) / 안 만들 것 / 가정 / 한계.
- 한계는 숨기지 않는다. 안 되는 것·확인 못 한 것은 여기에 적는다.

### 7줄 — LOG (5칸 + 고정 절)
- 본표: 단계 | 내가 지시한 것 | AI가 한 것 | 내가 직접 확인한 것 | 시각.
- 고정 절 **"AI 위임 vs 직접 검증"**: 맡긴 것 | 내가 확인한 것 | 어떻게 | 숫자. 본표와 섞지 않는다. '맡긴 것' = AI가 만든 코드·스크립트·초안·리뷰. '내가 확인한 것' = 내가 직접 눈으로 본 화면·원본 행·담당자 답 n건과 그 값.
- 내가 "기록만 해라: …"라고 하면 그 내용만 LOG에 적고 다른 작업은 하지 않는다.

### 8줄 — DECISIONS·VERIFY·테스트
- DECISIONS: 결정 | 대안 | 약점("어떤 조건이면 무엇이 얼마나 바뀌나", 숫자로) | 검증. 본문은 내가 쓴다 — 너는 대안·약점 후보만 준다.
- VERIFY: 무엇 | 명령 | 결과 숫자 | 파일.
- 테스트는 tests/에, 기능마다 정상·경계·오류 각 1개 이상. 실행 명령과 출력 전체를 out/test_result.txt에 남긴다(node면 `node --test`, 폴더 인자 없이 또는 `tests/*.test.js`).

### 10줄 — S2 질문 초안
- 질문 상한·DM 문장은 `_playbook/ASK.md`(README가 두꺼우면 REQUIREMENTS에서 숫자 없는 행만 묻는다 — `$ask`), 전체 순서는 `/tmp/harness/refs/QUESTION_BANK.md`. 담당자는 "할 일·기능 목록을 알려 달라"에는 답하지 않으니 장면·기준·숫자·경계를 하나씩 묻는다. 처음 3분은 해법 단어(자동화·AI·기능·화면) 금지, 기술을 묻지 않는다.
- 빠뜨리지 말 것: 성공 숫자(지금 값 → 목표) / 안 해도 되는 것 / 날짜 붙은 기준이 지금도 맞나 / 뺄 데이터 / 코드값·상태값의 뜻과 대상 / 예외·동률·중복·취소·기준값과 딱 같을 때 / 공개하면 안 되는 이름·번호·금액.
- inventory에서 센 것(완전 중복·이상 값·낯선 코드값)은 "어떻게 처리할지"까지 묻는다.
- 초안을 LOG에 쓰고, 한 번에 하나씩 보낸다(답이 오면 같은 자리를 한 번 더 판다). 보낸 뒤 답을 기다리지 않고 inventory 확인·PLAN 초안을 이어 간다. PLAN 확인을 받기 **전에** 초안의 질문을 전부 보낸다. 답끼리 부딪히거나 한 답이 두 뜻이면 놓치면 비싼 쪽으로 잠정하고 DECISIONS에 적은 뒤 확인을 묻는다.

### 11줄 — S5·S6
- S5: 서버를 띄우고 `curl -s -w "\n%{http_code}\n"` 출력(상태 코드 포함)을 out/browser_check.txt에. 미리보기 화면 확인은 내가 하고 "기록만 해라"로 LOG에. 결과를 바꾼 뒤에는 S5를 다시 돌린다.
- S6: 새 터미널에서 codex를 열어 리뷰어 역할 — 테스트를 다시 돌리고, 문서 숫자를 out/과 대조해 지적만 VERIFY에 적는다. 리뷰어는 고치지 않는다. 고칠 것은 내가 골라 메인 세션에 시킨다.

### 12줄 — 변경·긴 대화
- 담당자 합의나 요구가 바뀌면 코드보다 PLAN을 먼저 고치고 LOG에 시각을 남긴다.
- 대화가 길어지면(경과 100분 또는 S4 두 번째 기능 뒤 — 미루지 않는다) LOG를 갱신하고, 새 터미널에서 codex를 열어 AGENTS.md → PLAN → LOG 순으로 읽고 현재 단계를 5줄로 보고한 뒤 이어 간다.
- 내가 `STATE`라고만 치면 다른 작업 없이 세 줄: 지금 단계 / 남은 시간(LOG 시각 기준) / 검증 안 된 체크.
