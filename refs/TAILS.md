### S2 확인 답에 고칠 점·넘긴 판단이 있을 때 (①~④ 순서대로)

1. **고칠 점 반영** [뒤에 붙이기] — 뒤에 담당자 답 전체를 붙인다:
   ```
   담당자가 PLAN 확인에서 아래를 고쳐 달라고 했다. date로 시각을 찍어 담당자 답을 LOG에 원문 그대로 적고, 해당 칸만 고쳐라. 고친 칸을 보여 주고 커밋하지 말고 멈춰라. 담당자 답:
   ```
   → **내가 확인**: PLAN.md를 열어 담당자가 말한 점이 그 칸에 분명히 들어갔는지 본다.
2. **넘겨받은 판단** — 위 S2 꼬리 상황 "판단해 주세요"의 두 상자(추천 요청 → 내 선택)를 보낸다. 넘긴 것이 없으면 건너뛴다.
3. **재확인 DM** [그대로]:
   ```
   방금 고친 PLAN 칸과 내가 정한 처리 규칙만 담아, 담당자에게 보낼 재확인 DM을 두세 문장으로 써라. 판단을 넘겨받은 항목은 "이렇게 정했습니다, 이유는 …"으로 쓰고 "이대로 진행해도 될까요?"로 끝내라. 보내지 마라.

   → 복사해 DM으로 보낸다.
4. **확인 시각 기록** — 담당자가 "그대로 맞다"고 하면 S2-4의 상자([뒤에 붙이기])에 그 답을 붙여 보낸다. 또 고칠 점이 나오면 1로 돌아간다.

## 확인 문장 예시 — "기록만 해라: 내가 직접 확인한 것 —" 뒤에 붙이는 것 (단계별)
채점 AI는 "AI 결과를 직접 검증하고 수정했는지"를 대화 로그·LOG에서 찾고, 서술형 2번이 바로 그걸 묻는다. 그래서 **내가 눈으로 본 것·바꾼 것을 단계마다 한 행씩** 남긴다. 문장 틀은 셋: **무엇을 / 어떻게(어디서) / 숫자 또는 결과**. 반드시 실제로 본 것만 — 확인 안 한 것을 적으면 서술형에서 되물을 때 무너진다.
```
S1  기록만 해라: 내가 직접 확인한 것 — out/inventory.md의 완전 중복 3건 중 1건(id 1042)을 원본 orders.csv에서 Ctrl+F로 찾아 같은 행이 두 번 있는 것을 봤다. -1이 4건인 열은 금액 열이며, 그중 1건(id 2210)을 열어 보니 취소 건이었다. ID 열은 order_id가 맞다(두 파일에 모두 있고 줄마다 다름).
S2  기록만 해라: 내가 직접 확인한 것 — 담당자 답 3건을 LOG 원문과 대조했다. "오래된 건 빼"는 날짜가 아니라 status=CLOSED 기준이라고 되물어 확인받았다(10:41). PLAN 성공 기준 "누락 0건 → 지금 12건"은 담당자가 말한 숫자다.
S3  기록만 해라: 내가 직접 확인한 것 — Codex가 server.js를 localhost로 띄우려 해서 0.0.0.0으로 고치게 했다. 내가 새 탭에서 PORT=3000 node server.js로 띄우고 curl /health 200과 Browser 도구 / 화면을 봤다.

S6  기록만 해라: 내가 직접 확인한 것 — 리뷰어 지적 4개 중 2개(날짜 경계, 빈 입력)만 반영하기로 골랐다. 나머지 2개는 범위 밖이라 VERIFY에 "미반영·이유"로 남겼다. 반영 뒤 테스트 9/9, curl 200을 다시 봤다.

## 공통 — 중간에 새 사실이 나왔을 때 (꼬리 질문 순서)
언제 쓰나: 대조·리뷰·결과 확인에서 "빠진 것"이 나왔을 때 / 담당자 답이 두 뜻이거나 "판단해 달라"고 했을 때 / 원본에서 예상 밖의 줄을 봤을 때 / 요구가 바뀌었을 때.
순서는 늘 같다: **① 기록 → ② 사실 확인 → ③ 물을지 정하기 → ④ PLAN·DECISIONS 먼저 반영 → ⑤ 원래 단계로.** 코드는 ④ 다음에만 고친다.

**물을지, 내가 정할지**
| 상황 | 처리 |
|---|---|
| 결론(누가 대상인가, 기준값, 무엇을 빼나)이 바뀔 수 있다 | 반드시 담당자에게 묻는다 |
| 담당자가 "판단해 달라"고 했다 | Codex에게 선택지·추천을 받고 내가 고른다. 기본은 놓치면 비싼 쪽(누락 방지). 이유를 DECISIONS에, 결과 확인(S5) 때 다시 보여 준다 |
| 표기·형식만의 문제(공백, 대소문자, 날짜 형식) | 내가 정하고 DECISIONS에 한 줄 |
| 새 사실이 여러 개 | 2~3개씩 모아서 한 번에 묻는다 |

1. **기록** — 담당자 답이면 S2-2 상자([뒤에 붙이기]) 그대로. Codex 보고에서 나온 것이면 기록하지 않고 2로.
2. **사실 확인** [뒤에 붙이기] — 뒤에 Codex가 "빠진 것"으로 보고한 줄이나 담당자가 말한 항목을 붙인다:
   ```
   아래 항목을 원본 데이터에서 찾아 해당 줄 예시와 건수를 보여 주고, 이미 아는 항목(inventory의 완전 중복·빈칸·표시값 등)과 같은 것인지 한 줄로 말해라. 해석·처리하지 말고 멈춰라. 항목:
   ```
   → **내가 확인**: 예시 줄을 원본에서 Ctrl+F로 직접 찾아본다. 이미 아는 항목과 같은 것이면 새로 물을 필요가 없다(4로).
3. **꼬리 질문** [그대로] — 물어야 할 때:
   ```
   방금 확인한 사실을 근거로 담당자에게 보낼 꼬리 질문을 써라. 건수와 예시 줄 하나를 넣고, 내가 잠정한 처리(놓치면 비싼 쪽)를 함께 적어 "이렇게 처리해도 될까요?"로 끝내라. 해법을 정하지 말고 보내지 마라.
   ```
   → 복사해 DM으로 보낸다. 답은 1번(S2-2 상자)으로 기록.
4. **반영** — 담당자 답이 근거면 [그대로]:
   ```
   LOG의 최신 담당자 답을 근거로 PLAN '데이터 처리 규칙'(필요하면 다른 칸)을 고쳐라. 바뀐 칸과 근거 시각을 한 줄씩 말하고, DECISIONS에 넣을 대안·약점 후보를 한 줄씩 보여 줘라. PLAN만 고치고, git log에서 지금 단계 번호를 찾아 "[S n/6] 규칙 보완(담당자 HH:MM)" 형식으로 커밋해라. 이미 만든 코드가 이 변경의 영향을 받으면 무엇이 바뀌는지만 말하고 고치지 마라.
   ```
   담당자가 판단을 넘겼거나 내가 정할 일이면, S2 꼬리 상황 "판단해 주세요"의 두 상자(추천 요청 → 내 선택)를 쓴다. 단계 번호는 Codex가 git log에서 찾아 붙인다.
   → DECISIONS 본문은 S5 `$decide`에서 번호로 고른다. 지금은 후보만 받아 둔다.
5. **원래 단계로**
   - 데이터 처리 규칙이 바뀌었으면 → S4-2(changes_log)를 다시 보낸다(바뀐 항목의 전후 행이 새로 쌓인다).
   - 이미 만든 기능이 영향을 받으면 → S5-4 상자(요구 변경)로 그 부분만 고친다.
   - 아무 영향이 없으면 → 하던 단계의 다음 상자로.
