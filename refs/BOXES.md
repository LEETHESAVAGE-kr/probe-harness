# BOXES — PROMPTS.md의 원본 (이름 = 명령 이름)

> 시험 중엔 이 파일이 아니라 `_playbook/PROMPTS.md`를 연다. PROMPTS.md는 이 파일에서 `node scripts/gen_prompts.mjs`가 만든다(손으로 고치지 않는다) — 블록 = `$이름` + 상자 본문 + 아래 '지시:' 4줄.
> 상자 본문의 `{…}`는 Codex가 채우는 자리, 지시 4줄의 `<…>`는 내가 바꾸는 빈칸이다.
> 하네스가 `./.harness`에 있으면 상자 속 `/tmp/harness`를 `./.harness`로 읽는다.
> `.agents/skills/<이름>/SKILL.md`가 있는 명령은 그 파일이 원본이다. 이 파일의 상자는 같은 지시를 짧게 줄인 것이다.

## prompt
지시 틀과 반응 문장의 전체판. RUN 머리에 같은 것이 있다. 빈칸 `<…>`만 이 과제의 말로 바꾼다 — 과제 값(인원·시각·기능명)은 미리 적어 두지 않는다.
```
$명령 <R번호> 목적: <왜 지금 이걸 하나> — 근거: <담당자 HH:MM 답 또는 README:줄>
범위: <이번에 할 것만> / 하지 마라: <다음 R번호·요구 밖 기능> / 고칠 파일: <파일>
내 판단: <내가 정한 기준·방식> — 이유: <한 줄(더 단순한 쪽을 고른 이유 등)>
확인: 끝나면 내가 <out 파일·테스트 이름>에서 <무엇을 숫자로> 본다
```
| 줄 | 제출물에서 읽히는 것 | 빠지면 |
|---|---|---|
| 목적·근거 | 문제·목표를 스스로 정했나, 맥락 유지 | "해 줘"형 위임 |
| 범위·하지 마라 | AI에게 끌려가지 않았나(요구 밖 기능 차단) | 과설계 방치 |
| 내 판단·이유 | 결정 근거, 분해·위임 설계 | AI가 정한 것을 따라감 |
| 확인 | 검증 루프 | "완료"를 그대로 믿음 |

반응 문장(결과를 받은 직후):
```
방금 넣은 <기능>은 요구에 없다(<R번호> 원문: <…>). 되돌리고 DECISIONS '거부한 것'에 이유 한 줄.
결과 중 <n>건(첫 행·경계·마지막 행)을 내가 원본과 대조한다. 그 행의 원본 위치와 계산값만 보여라.
<테스트·코드>의 값을 <지금 값 → 맞는 값>으로 바로잡는다. 근거 <담당자 HH:MM>. 실패를 먼저 보이고 고쳐 통과시켜라.
<담당자 HH:MM> 답으로 <조건>이 바뀌었다. 코드보다 PLAN·REQUIREMENTS를 먼저 고치고 영향받는 테스트 이름만 말해라. 커밋 메시지는 요구 변경(<HH:MM>).
같은 지시로 두 번 실패했다. 다시 시키지 않는다 — $debug 증상: <…>
실행한 명령과 통과·실패 개수를 붙여라. 안 돌렸으면 미검증.
```

```

확인: 끝나면 내가 git show --stat의 양식 파일 수와 보고의 규칙 요약 한 줄을 본다
/status:
```

## s1
```
node /tmp/harness/scripts/readme_to_requirements.mjs 를 실행해 명령과 출력을 붙여라(README.md와 제공 데이터는 읽기만). 출력 첫 줄의 "요구 n · 규칙 n · 산출물 n"을 REQUIREMENTS.md 표 행 수와 대조해 한 줄로 말하고, "경고:" 줄은 그대로 다시 보여라. "번호 목록 요구가 0개" 경고면 README 문단마다 요구를 원문 그대로 행으로 옮기고 종류 칸에 '요구(번호 없음)'로 표시한 뒤 진행해라(묻지 마라). "덮어쓰지 않았다" 경고면 out/REQUIREMENTS.new.md에만 있는 행을 목록으로 보여라(옮기지 마라). README·data/README.md·*_SCHEMA.md에서 표로 뽑히지 않은 해석 제약 문장("~는 실적에서 빠진다" 등)은 원문 그대로 REQUIREMENTS 끝에 '규칙' 행으로 더하고 출처 — 파일:줄을 달아라. 출력의 "뼈대 추천"·"명령:" 줄을 보여 주고 부품마다 근거 줄(README.md:n)이 맞는지 한 줄로 말해라(깔지는 마라). 생성된 껍데기 목록을 보여라(내용은 채우지 마라). 데이터 파일을 전부 찾아 파일마다 대상을 가리키는 ID 열을 골라 이유를 한 줄로 말하고 node /tmp/harness/scripts/inventory.mjs {데이터 파일 전부} --by {그 열} --out out/inventory.md 를 실행해 출력을 붙여라(CSV가 없으면 인자 없이 --out만, 데이터가 없으면 "데이터 없음"). README가 2,000줄 이상이거나 범위 줄에 '장문'이 있으면 표에 '근거 절'·'★' 열(★은 제출물·평가·반드시 절에 걸린 행만)을 더하고, 배경·사례·등장인물·목차 절의 행은 표 아래 '## 후보(요구인지 담당자에게 확인)'로 내리고, out/examples.md에 예시 자리를 절 이름과 함께 뽑아 입력→출력 쌍을 표로(없으면 "예시 없음") 쓰고, 표 머리·행 번호는 그대로 두고, 보고 맨 첫 줄을 '요구 n행(★ k) · 후보 m · 예시 쌍 p'로(이번 목적은 둘째 줄) 해라. 해석·구현·만들 것 칸 채우기는 하지 마라. LOG 본표에 S1 한 행을 쓰고 [S 1/6] 요구 n·규칙 n·산출물 n, 껍데기 n 으로 커밋한 뒤 git show --stat HEAD를 붙이고, 끝에 '서사: 누가·무엇을·언제 정하나' 한 줄(README 배경의 원문 단어로, PLAN '사용자' 후보)을 쓴 뒤 멈춰라.
```
지시:
```
목적: README 요구를 하나도 빠뜨리지 않는 전수표를 만든다 — 근거: README.md 전체와 링크한 데이터·스키마 문서
범위: REQUIREMENTS·껍데기·inventory / 하지 마라: 해석 · 구현 · README 수정 / 고칠 파일: REQUIREMENTS.md · 껍데기 · out/inventory.md · out/examples.md · LOG.md
내 판단: <번호 없는 문단도 요구 행으로/번호 목록만 요구로> — 이유: 빠진 요구가 가장 비싸다
확인: 끝나면 내가 REQUIREMENTS 행 수가 README 번호·규칙 불릿·백틱 파일·제외의 합과 같은지 본다
```
언제: S1 · 8~30분, A 탭에
비울 칸: 선택지 ← README에 번호 목록이 있나.

## ask
```
REQUIREMENTS의 Q(지목) 행부터 시작해(README가 "담당자에게 확인"이라고 지목한 조건, Q 행이 없으면 README에서 같은 문장을 찾아라) 그 행마다 숫자(상한·우선순위·예외)가 나올 질문을 2~4개씩 만들어라. 단 초안의 첫 두 행은 항상 DM 1과 DM 2다(위 질문은 그 뒤). DM 1 = '이 데이터에서 [항목 하나]를 넣으면 결과가 어떻게 나와야 하나요? 한 건만' — [항목 하나]는 out/examples.md에 예시 쌍이 있으면 그 예시의 실제 항목 이름으로, 없으면 out/inventory.md에서 가장 건수가 많은 파일의 첫 행 ID로 채워라. DM 2 = '저는 이 과제를 [입력]을 [규칙]으로 [출력]으로 이해했습니다. 맞나요?' — [입력]·[출력]은 REQUIREMENTS ★ 행과 산출물 행의 원문 단어로, [규칙]은 README 요구 문장에서 동사 하나로. 셋째 행은 '제일 먼저 확인하고 싶으신 건 뭘까요?', 넷째는 두 갈래로 읽히는 규칙이 있을 때만 '[규칙]이 A로도 B로도 읽히는데 어느 쪽인가요?'. 그다음부터 지목 조건 순서. 행 하나 = 메시지 하나, [ ]를 남기지 마라. 그다음 REQUIREMENTS.md에서 숫자가 없는 행·모호한 말(적당히·빠르게·필요하면·자주·최적)이 있는 행·예외·경계가 안 적힌 행을 골라라. out/inventory.md에서 센 숫자(완전 중복·빈칸·낯선 코드값)는 관련 질문에 넣어라. out/examples.md가 있으면 예시 쌍의 입력값을 관련 행의 질문에 그대로 써라. 요구가 4개 이하로 README가 얇으면 대신 _playbook/ASK.md의 장면 → 기준 → 숫자 순서로 써라. 질문은 한 문장, 앞에 [R번호], 숫자가 필요하면 숫자를 제안하는 형태("{n}분 넘으면 안 쓰시는 편인가요, {m}분인가요?")로. 개수 상한 없음 — 대신 우선순위 순(지목 조건 → 결론을 바꾸는 것 → 나머지)으로 번호를 매겨라. 해법 단어(자동화·AI·기능·화면·대시보드)·기술 용어(API·스키마·엔드포인트)·"할 일을 알려 달라"는 쓰지 마라. LOG '담당자 대화'에 | 시각 | 초안 | [번호] 질문 | 답 태그 | 행으로 적고 번호를 붙여 보여 준 뒤 멈춰라. 보내지 말고 커밋하지 마라.
```
지시:
```
목적: README가 지목한 조건의 숫자를 받는다 — 근거: README:<줄>
범위: 질문 초안만 / 하지 마라: 보내기 · 해법 단어 · 기술 질문 / 고칠 파일: LOG.md '담당자 대화'
내 판단: <결론을 바꾸는 질문을 위로/지목 조건만 먼저> — 이유: 답 하나로 대상 건수가 바뀐다
확인: 끝나면 내가 지목 조건마다 숫자 제안형 질문이 있는지 본다
```
언제: S2 · 30분~, A 탭에
비울 칸: 줄 ← README의 "담당자에게 확인" 문장 · 선택지 ← 지목 조건이 몇 개인가.

## plan
```
LOG '담당자 대화'의 답 원문(시각 포함)과 README·REQUIREMENTS 원문만 근거로 PLAN 7칸(문제 / 사용자 / 성공 기준: 지금 값 → 목표 값 / 만들 것 / 안 만들 것 / 가정 / 한계)과 '## 데이터 처리 규칙' 절의 4칸 표(inventory 항목마다 처리 한 줄과 근거, '요구 목록' 표에 섞지 마라)를 채워라. REQUIREMENTS.md의 모든 행을 '만들 것/안 만들 것' 칸에서 둘 중 하나로 정하고(빈 행 0, 빠진 번호 0개), 안 만들 것에는 사유를 적어라. 만들 것 중 이번 구현 순서 상위 3개에 ★. PLAN '요구 목록'의 줄기·묶음 열: 요구(R) 행이 8개 이하면 "—", 9개 이상이면 같은 모듈 2~3행을 묶음 번호로 묶고 줄기 A/A2(뼈대가 주는 행은 '확인만'), '소유 파일 분할' 절에 줄기별 파일(같은 파일을 두 줄기에 넣지 마라). 이미 사람이 적은 칸은 바꾸지 마라. 더 단순한 방법과 더 정교한 방법이 갈리면 단순한 쪽을 만들 것에, 정교한 쪽은 PLAN 한계에 '대안(D1 대안)'으로. 담당자 답이 두 뜻이면 놓치면 비싼 쪽으로 잠정하고 가정에 "잠정 — 확인 필요". 근거 없는 칸은 "미확인". 서로 동시에 성립할 수 없는 행이 있으면 두 행 번호와 이유를 보고 끝 '충돌:' 줄로(어느 쪽을 먼저 지킬지는 내가 DECISIONS D7에). 다 채우면 _playbook/ASK.md 합의 확인 형식의 확인 DM(5줄 이내, 기술 용어 없이)을 보여 주고 멈춰라. DM은 보내지 말고 커밋하지 마라.
```
지시:
```
목적: 구현 전에 담당자와 범위를 맞춘다 — 근거: 담당자 답 <HH:MM 목록>
범위: PLAN 7칸 · REQUIREMENTS 만들 것/안 만들 것 / 하지 마라: 구현 · 커밋 · DM 보내기 / 고칠 파일: PLAN.md · REQUIREMENTS.md
내 판단: ★1은 <R번호>, 안 만들 것은 <README 제외/X행> 사유로만 — 이유: 범위는 자르지 않고 얇게 전부 만든다
확인: 끝나면 내가 만들 것/안 만들 것 빈 행 0과 ★ 3개를 본다
```
언제: S2 · 질문이 끝나면(늦어도 48분), 창 1에
비울 칸: HH:MM ← LOG 담당자 대화 · R번호 ← 결론을 바꾸는 행 · 사유 ← 행마다.

## algo
```
README의 그 행이 나온 절·REQUIREMENTS 그 행·LOG '담당자 대화'만 근거로 out/algo_R{번호}.md를 써라. 표 | 후보 | 한 줄 원리 | 담당자 기준 충족 | 구현 시간(분) | 네 문장 설명 가능 | 입력 10배 | 약점 | 3행(단순→정교), 끝에 "기준을 만족하는 가장 단순한 것: 후보 n" 한 줄. 코드를 쓰지 말고 외부 패키지를 전제하지 마라. 근거 없는 기준은 "미확인". 고르는 규칙: 기준 미충족을 빼고 남은 것 중 가장 단순한 것을 추천, '네 문장 설명 가능 = 아니오'인 후보를 내가 고르면 "설명 불가 — 서술형 리스크" 한 줄을 경고하고 진행. 보고 5줄 끝에 "후보 n이라고 답해라"를 쓰고 멈춰라. 내가 답하면 DECISIONS.md D1 칸에 "결정: 후보 n — 원리 한 줄 / 대안(더 단순): 후보 k — 기준 미충족 사유 / 대안(더 정교): 후보 m — 안 한 이유"를 쓰고, PLAN.md '만들 것' ★1 행의 '규칙 한 문장' 칸(없으면 만든다)에 고른 후보의 한 줄 원리를 쓰고, [S 2/6] 알고리즘 선택 R{번호} 로 DECISIONS.md·out/algo_R{번호}.md·PLAN.md만 커밋한 뒤 git show --stat HEAD를 붙이고 멈춰라.
```
지시:
```
목적: 핵심 행의 방식을 근거로 고른다 — 근거: <README 절·담당자 HH:MM 답>
범위: <R번호> 후보 표만 / 하지 마라: 구현 · 패키지 설치 / 고칠 파일: out/algo_R번호.md · DECISIONS.md · PLAN.md
내 판단: 후보는 <단순/정교> 쪽부터 본다 — 이유: 네 문장으로 설명되는 쪽이 서술형 재료다
확인: 끝나면 내가 후보 3행과 기준 충족 칸, 추천 한 줄을 본다
```
언제: S2 · `$plan` 직전, 창 1에(핵심 행마다 · 8분 상한)
비울 칸: README 절·HH:MM ← LOG 담당자 대화 · R번호 ← 최적·배치·경로·일정·매칭 동사의 행 · 선택지 ← 하나만. 끝 질문에는 `후보 n`으로만 답한다.

## s3
```
서버 뼈대를 만들어라. PLAN에서 정한 부품으로 node /tmp/harness/bootstrap.mjs --scaffold node-v2 --with {부품}을 이미 깔았으면 그 server.js에서 시작하고(아래 중 이미 있는 것은 다시 만들지 마라), README가 다른 언어를 정했으면 이 상자 대신 traps 상자를 써라. 아니면 node 내장 http만. 0.0.0.0, PORT 환경변수(기본 3000), GET /health 200, 로그인 1개(역할 2개, 데모 계정 2개를 빈 저장소에서 시작해도 만들고 HOW_TO_RUN 데모 계정 칸에 적을 것은 C에게 요청으로), 쿠키는 HttpOnly만. 라우팅 순서(진입점→인증→검증→계산→저장→응답)를 바꾸면 그 함수 머리에 // [D6] 주석 한 줄. 설정값은 전부 기본값을 둔다. 시작·테스트 명령을 README_RUN.md에, 스모크 테스트 1개(테스트 서버는 PORT=0), 출력은 out/test_result.txt에. 요구 밖 기능은 만들지 마라. 통과하면 [S 3/6] 커밋하고 git show --stat HEAD를 붙인 뒤 멈춰라.
```
지시:
```
목적: 확인하는 사람이 들어올 길(0.0.0.0·/health·로그인)을 먼저 연다 — 근거: README 실행 요구
범위: 깔린 뼈대 위 서버·스모크 테스트·README_RUN / 하지 마라: 요구 밖 기능 · 서버 직접 실행 / 고칠 파일: server.js · src/ · tests/smoke · README_RUN.md
내 판단: 로그인은 <역할 두 개·데모 계정 두 개/없음(README 범위 밖)> — 이유: 확인하는 사람이 그 길로 들어온다
확인: 끝나면 내가 out/test_result.txt의 스모크 통과와 curl /health 200을 본다
```
언제: S3 · 48~55분, A 탭에(창 6에서 --scaffold node-v2를 깐 뒤)
비울 칸: 선택지 ← README에 로그인·역할 요구가 있나.

## feat
```
REQUIREMENTS.md에서 '만들 것'이고 상태가 빈 첫 행 하나만 만들어라. 시작 전에 세 줄(범위·고칠 파일 / 테스트 3개 이름: 정상 / 경계: 담당자 기준값과 딱 같은 값 / 오류: 없는 ID·빈 값 / 끝 조건)과 이 기능이 쓰는 시그니처 슬롯 한 줄(D1~D6, 없으면 "없음")을 말하고 진행해라. 더 단순한 방법이 있으면 그것을 먼저 만든다. 테스트를 먼저 쓰고 실패를 본 뒤 구현해라. 테스트 이름 앞에 [Dn], 슬롯을 쓰는 함수 머리에 // [Dn] 주석 한 줄. 테스트는 tests/에, 출력은 out/test_result.txt에. 소유 밖 파일은 건드리지 마라. 통과하면 커밋하지 말고 4문장 퀴즈를 내라: 코드와 대조해 문장 4개(1 무엇을 / 2 어떤 순서로 / 3 왜 그렇게 / 4 어디서 틀리나)를 각각 A/B 두 판으로 — 하나는 코드와 맞고 하나는 미묘하게 틀리게(순서·경계·포함/제외·숫자 중 하나만 바꿈), 정답 자리는 섞고 말하지 마라. 끝에 "1A 2B 3A 4B처럼 답해라"라고 쓰고 멈춰라. 내가 답하면 틀린 고름 수를 세어 2개 이상이면 커밋하지 말고 틀린 번호와 "(가) 단순화 / (나) 제외" 두 선택지를 보여 주고 멈춰라. `가`를 받으면 더 단순한 방식으로 바꾸고, 지금 방식은 PLAN 한계에 '대안(D1 대안)'으로 적고, 바꾼 뒤 퀴즈를 다시 낸다. `나`를 받으면 REQUIREMENTS 그 행을 "안 만듦 — 설명 불가"로 고치고 멈춘다. 1개 이하면 REQUIREMENTS 그 행의 상태(`됨 [S 4/6]`)·파일·테스트 칸을 채우고, LOG '## 설명 카드'에 카드 1장(`### 카드 n — 기능` 아래 `- 파일·함수:` `- 근거:` `- 테스트:` `- 바로잡은 것:` `- 기법:` `- 약점:` `- 내 4문장:` 맞는 판 네 문장 + "(퀴즈 정답 n/4)")을 붙인 뒤 [S 4/6] R{번호} {한 줄} (Dn {기법}) 으로 커밋하고 git show --stat HEAD를 붙여라. 보고 끝에 DECISIONS Dn 후보 문장 한 줄, 바로잡은 것이 "없음"이면 리스크에 [거부 기록 0건]. 범위 줄에 '묶음: R3 R4 R5'가 있으면 같은 모듈 행만 최대 3행(어긋나면 "묶음 불가: R5는 다른 모듈 — 따로 쳐라"로 멈춤), 행마다 계획·테스트 1개 이상·구현, 경계 테스트는 묶음 전체에서 1개 이상, 퀴즈는 묶음당 한 번(문장마다 R 표시), 카드와 상태 칸은 행마다, 커밋은 묶음당 1회 [S 4/6] R3-R5 {한 줄} (Dn), 보고 첫 줄에 경과 분, 한 행이 실패하면 그 행만 git checkout으로 되돌리고 나머지로 커밋한 뒤 "R4 실패 — A2로". 그리고 멈춰라.
```
지시:
```
목적: <R번호> 행의 성공 기준을 만족시킨다 — 근거: 그 행의 담당자 답(LOG 담당자 대화)
범위: <얇게: 최소 동작 1 + 테스트 1/깊게: 지표 1 + 규칙 1> / 하지 마라: 다음 R번호 · 요구 밖 기능 · 새 패키지 / 고칠 파일: src/ · tests/feat_*
내 판단: <정렬 한 번/표 한 장/규칙 한 줄>로 먼저 — 이유: 4문장으로 설명되는 쪽, 정교한 쪽은 PLAN 한계에 (D1 대안)
확인: 끝나면 내가 경계 테스트에서 담당자 기준값과 딱 같은 경우의 결과를 본다
```
언제: S4 · 55~150분, A 탭에(행마다 한 번)
비울 칸: R번호 ← REQUIREMENTS 상태 빈 첫 행 · 범위 ← ①이면 얇게, ②면 깊게(같은 모듈 2~3행이면 범위 칸 맨 앞에 `묶음: R3 R4 R5`) · 선택지 ← 하나만 남긴다.

## prove

## traps

## decide
```
PLAN·REQUIREMENTS·LOG(본표의 "기록만 해라" 행·설명 카드·담당자 대화)·DECISIONS·코드 [Dn] 주석·tests/·out/만 근거로, 파일은 아직 쓰지 말고 표만 보여라. ① DECISIONS 슬롯 D1~D6과 '거부한 것'마다 | 칸 | 후보 | 표: 결정 후보 A/B(코드·PLAN·담당자 답에서, 지금 코드가 고른 쪽이 A) / 이유 후보 ①②③(한 줄씩, 그중 하나는 "더 단순한 쪽이 4문장으로 설명되어서" 류) / 대안(더 단순 · 더 정교) / 약점(조건·숫자는 out/ 파일에서만, 없으면 [기록 없음]) / 검증(테스트 이름·out 파일). 해당 없는 슬롯은 "A: 해당 없음 — README 범위 밖" 후보 하나, 거부 기록이 없으면 "A: 거부 기록 없음" 하나(꾸며 내지 마라). ② LOG "AI 위임 vs 직접 검증" 고정 절 초안을 "기록만 해라" 행·설명 카드·out/ 숫자에서 | # | 맡긴 것 | 내가 확인한 것 | 어떻게 | 숫자 | 표로(행마다 출처). ③ 끝에 "번호로 답해라: 예 D1-A②, D2-B①, 거부-A③, 고정 절 '맞다' 또는 '3번 빼라'"라고 쓰고 멈춰라. 내가 답하면 DECISIONS 각 슬롯 결정 칸에 "내 선택: A — 이유: ② {그 이유 후보 문장}"(내가 이유를 직접 쳤으면 그 문장), 대안·약점·검증은 표 그대로, 답에 없는 슬롯은 건드리지 말고, LOG 고정 절은 뺀 행을 빼고 확정 표로, LOG 본표에 | S5 | $decide 선택 D1-A② … | 슬롯 표·고정 절 초안 | 내가 고른 것 n건 | 시각 | 한 행을 쓴 뒤 [S 5/6] 결정·검증 기록 으로 DECISIONS.md·LOG.md만 커밋하고 git show --stat HEAD를 붙이고 멈춰라.
```
지시:
```
목적: DECISIONS 슬롯과 LOG 고정 절을 내 선택으로 채운다 — 근거: LOG "기록만 해라" 행·설명 카드·out/
범위: 슬롯 표·고정 절 초안을 보여 주고 번호 답 기다리기 / 하지 마라: 내 답 전 파일 쓰기 · 근거 없는 숫자 / 고칠 파일: DECISIONS.md · LOG.md
내 판단: 이유는 <이유 후보에서 고른다/직접 한 줄 친다> — 이유: 내가 고른 이유가 서술형 답이 된다
확인: 끝나면 내가 DECISIONS 결정 칸의 '내 선택' 수와 git show --stat HEAD를 본다
```
언제: S5 · 측정 커밋 뒤(150분쯤), 창 1에
비울 칸: 선택지 ← 후보에 내 이유가 있나. 표가 오면 `D1-A② D2-B① 거부-A③ 고정 절 맞다`처럼 번호로만 답한다.

## 한 줄 지시
> 명령이 아닌 붙여 넣기 문장. `gen_prompts.mjs`가 항목마다 PROMPTS.md 블록 하나를 만든다. 반응 6개의 본문은 위 prompt 상자의 반응 블록(순서대로)이다.

### 역할 카드
언제: S0~S6 · s0 보고에 "이번 목적:"이 없어 `$role-a~d`가 안 먹을 때, 창 2·4·5·7 각 탭에
```
.agents/skills/role-<a/b/c/d>/SKILL.md를 읽고 그 카드대로 일해라. 카드 마지막 줄대로 말하고 멈춰라
```
비울 칸: 역할 ← 창 2는 a · 창 4는 c · 창 5는 d · 창 7은 b, 하나만 남긴다.

### 역할 시작
언제: S1·S3 · 역할 카드 보고를 받은 뒤, 창 4(C)는 A의 `$s1`이 끝나고 · 창 5(D)는 카드 보고 직후
```
방금 말한 첫 일만 해라. 끝나면 "커밋 준비됨"으로 멈춰라
```

### 기록-요구표
언제: S1 · 30분 전, A 탭에
```
기록만 해라: 내가 직접 확인한 것 — REQUIREMENTS <n>행이 README 합과 같고, 백틱 파일 중 없는 것 0개를 탐색기에서 봤다
```
비울 칸: n ← REQUIREMENTS 표 행 수.

### 숨은 제약
언제: S1 · data/README·스키마 md의 제약이 표에 없을 때, A 탭에
```
REQUIREMENTS 끝에 규칙 행으로 추가해라(원문 그대로, 출처 — 파일:줄): <원문>
```
비울 칸: 원문 ← data/README·스키마 md.

### 기록-담당자 답
언제: S2 · 답이 올 때마다, A 탭에
```
기록만 해라: date로 시각, 아래 담당자 답 원문을 LOG '담당자 대화'에 태그 <새 정보/확인/모름>로 — <답 원문>
```
비울 칸: 태그·원문 ← 담당자 답.

### 판단 넘김
언제: S2 · 담당자 답이 두 뜻이거나 "판단해 주세요"일 때, A 탭에
```
담당자가 넘긴 항목마다 선택지 A·B와 결과 숫자 차이, 추천 하나를 보여 주고 멈춰라
```

### 내 선택
언제: S2 · 판단 넘김 표를 본 뒤, A 탭에
```
내 선택이다: <1-A 2-B>. PLAN에 반영하고 DECISIONS 후보를 보여 줘라
```
비울 칸: 선택 ← 내 판단(이유가 서술형 재료).

### 기록-합의
언제: S2 · 담당자가 PLAN을 확인하면, A 탭에
```
기록만 해라: PLAN 합의 기록에 '확인 받은 시각: <HH:MM>'을 적고 C의 커밋 준비됨 목록(handoff.mjs)도 함께 [S 2/6] PLAN 합의 로 커밋한 뒤 git show --stat HEAD를 붙여라
```
비울 칸: HH:MM ← 담당자 확인 답 시각.

### 기록-로그인 화면
언제: S3 · Browser로 로그인 1회를 본 뒤, A 탭에
```
기록만 해라: Browser(<포트>, /)에서 로그인 화면 → 로그인 뒤 화면을 봤다. 보인 것: <화면 글자>
```
비울 칸: 포트 ← 창 8 · 글자 ← 화면.

### 첫 기능 커밋
언제: S4 · 첫 기능 커밋 때, A 탭에
```
C·D 가운데 C의 커밋 준비됨 목록(handoff.mjs)도 함께, D 목록이 있으면 그것도 같이 커밋하고 git show --stat HEAD를 붙여라
```

### 전후 기록
언제: S4 · 데이터를 빼·바꾸·합치기 전에, D 탭에
```
데이터를 <빼기/바꾸기/합치기> 전에 changes_log.mjs로 out/changes_log.md에 예상 행을 남기고, 처리 뒤 실제 행을 붙여라. 결론 칸은 결론 숫자를 전후로 한 번씩 돌려 채워라
```
비울 칸: 선택지 ← A의 세 줄 계획.

### 세션 교체-기록
언제: S4 · 120분, A 탭에
```
기록만 해라: LOG 본표를 채우고 LOG 끝 "## 인수인계" 3줄 뒤 커밋
```

### 세션 교체-새 탭
언제: S4 · 120분, 창 3 새 codex에
```
AGENTS.md → PLAN → REQUIREMENTS → LOG 순으로 읽고 지금 단계·다음 R번호·미검증을 5줄로 보고하고 멈춰라
```

### 기록-out 확인
언제: S5 · out/ 파일을 내가 연 뒤, A 탭에
```
기록만 해라: 내가 직접 확인한 것 — <out 파일>에서 <숫자>를 봤다
```
비울 칸: 파일·숫자 ← 내가 연 out/ 파일.

### 측정 커밋
언제: S5 · $verify·$screen 뒤, A 탭에
```
C·D의 커밋 준비됨 목록을 handoff.mjs로 모아 [S 5/6] 검증·측정 으로 커밋하고 git show --stat HEAD를 붙여라. 충돌이면 커밋하지 말고 보여 줘라
```

### 반영
언제: S6 · 리뷰 지적을 고른 뒤, A 탭에
```
아래 VERIFY 지적만 고치고 전체 테스트를 다시 돌려 통과·실패 개수를 붙여라. 다른 곳은 건드리지 마라: <V-번호들>
```
비울 칸: V-번호 ← VERIFY.md에서 내가 고른 것.

### 마감
언제: S6 · 172분 전, A 탭에
```
전체 테스트를 한 번 돌려 out/test_result.txt를 갱신하고, 못 한 것은 PLAN 한계에 한 줄씩 적은 뒤 C·B의 커밋 준비됨 목록과 함께 [S 6/6] 마감 커밋하고 git status를 붙여라
```

### 반응-요구 밖
언제: 결과에 요구 밖 기능이 보일 때(과제당 최소 1회), 그 결과를 낸 탭에
본문: 반응 1
비울 칸: 기능 ← 결과 보고 · R번호·원문 ← REQUIREMENTS.

### 반응-내가 검증
언제: 결과를 받은 직후, 그 탭에
본문: 반응 2
비울 칸: n ← 대조할 행 수(첫 행·경계·마지막 행).

### 반응-바로잡기
언제: 테스트·코드 값이 담당자 답과 다를 때, A 탭에
본문: 반응 3
비울 칸: 테스트·코드 ← 파일 이름 · 값 ← 지금 값과 담당자 값 · 시각 ← LOG 담당자 대화.

### 반응-의도 갱신
언제: 담당자 답으로 조건이 바뀌었을 때, A 탭에
본문: 반응 4
비울 칸: 시각 ← LOG 담당자 대화(커밋 메시지 칸도 같은 시각) · 조건 ← 바뀐 조건.

### 반응-접근 변경
언제: 같은 지시로 두 번 실패했을 때, 그 탭에
본문: 반응 5
비울 칸: 증상 ← 실패 출력 한 줄.

### 반응-숫자 없는 완료

본문: 반응 6
